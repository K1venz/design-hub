## 任务指定的追加验证

### cancel 路径（零成本）— PASS
费用卡（1 张 ¥0.4000）→ UI 点「取消」→ 气泡「已取消本次出图。」+ `assistant_end{complete}` → **同 token 重放** `action:confirm` → `error{invalid_confirm_token,"确认令牌无效或已过期，请重新发起。"}` → A 的 job 总数保持 3、无扣费。证据：`0048-chat-cancel-path.png`、`0048-cancel-turn-stream.txt`。（#884④ cancel 立即作废 token 实证）

### confirm_token 一次性/防错拒 — PASS
- 错误 token confirm → `invalid_confirm_token`，且**不消耗**用户有效 pending（费用卡确认/取消按钮仍在、其后取消成功）——session_store.take_pending 「不匹配不动有效 pending」语义实证（session_store.py:83-91）。
- cancel 后重放拒（见上）。

### 跨用户隔离 — PASS
用户 B 携 A 的 session_id+confirm_token `POST /chat/confirm(action=confirm)` → `error{bad_request,"会话不存在或无权访问"}`，B 无任何 job（GET /listing/jobs=[]），A 的 pending 不受影响。（owner 隔离在 session get 层，token 层不可达）

### confirm_token TTL 10 分钟 — PASS（实测）
- 代码语义：session_store.py:46 `ttl_seconds=600`；take_pending 对过期 token「匹配即消费+拒绝」（一次性与 TTL 叠加，过期 token 不可复活）。
- 实测：15:33:19 埋 pending（token ct_HXwyPRpP…，¥0.4000 未确认）→ 15:43:43 重放 confirm（存活 10min24s > 600s）→ `error{invalid_confirm_token,"确认令牌无效或已过期，请重新发起。"}`，job 数保持 3、零扣费。

### 会话级出图闸 session_job_limit（≤5 单/会话）— 代码核验（按预算纪律不真跑）
orchestrator.py:206-215：confirm 消费 token 后、启 job **前**查 `session.job_count >= max_session_jobs`（settings.chat_session_max_jobs=5，settings.py:30）→ 超限返回**明确** `error{session_job_limit,"本次会话出图已达上限（5 单），请开新会话。"}`，非静默丢弃（#884② 语义正确）。真跑需 5 单成功出图 ≈ ¥2+，未烧钱复测。

### 占位 ratio 转澄清（dev 2e0326a）— 实测 + 代码核验
- 诱导实测（新会话）：「比例随便，你看着办，用这张图出一张图就行。」→ 豆包按硬化系统提示填**合规默认** `ratio:"1:1", n:1` 干净进费用卡（估价 0.4000，已取消零成本）。放权语义→默认 1:1 是 2e0326a 设计内行为（系统提示「用户没指定就默认填 1:1」），非带病进确认；本轮未能诱导出占位值（真 LLM 该错误行为无法按需复现，如实注明）。
- 占位值拦截路径核验：orchestrator.py:141-151——`cost_confirm` **之前** `launcher.validate(user, req)`（与出图同一校验源，#884⑤），ValueError/NotFoundError → 自然语言「还差点信息、暂时没法出图（…）」转澄清 + `assistant_end{complete}`，不进费用闸。引 dev 记录：2e0326a 冒烟「mock E2E 全 PASS 含占位 ratio→转澄清必测（coordinator #905）」。

## 重要说明（如实记录）

① **任务前提修正：image-code/tests/ 下没有 chat 单测。** tests/ 现有 7 个文件（docs_gate/listing_history/listing_validation/prompt_cards/provider_contract/provider_resilience/throttle_and_pure）均不含 chat/confirm_token/session_job 断言。dev 对负向语义的覆盖是**手工 mock E2E**（ISSUE-0048 处理记录 + 2e0326a 冒烟），无可重跑自动化单测。本报告以「读实现代码核语义 + 零成本 API 负向实测（重放/跨用户/cancel/TTL）」补位完成验收；**建议（P2 测试债）dev 补 chat 负向 pytest**（token 一次性/TTL/跨用户/会话闸/validate 转澄清），否则后续重构无回归网。

② 会话初期公开首页出现过一次被跳 /login（/api/me 401 触发全局登出跳转）。确定性复测无法在 `/` 复现（公开首页不调 /me）；归因共享 Playwright 浏览器 profile 残留态（旧标签/旧token），非首页代码缺陷。附带核验：带失效 token 停留公开首页不会被驱逐。

③ 路径①的消息发送与 confirm 各有一次非本人显式操作的 POST（本 tab 网络日志 #111/#112）。归因测试驱动器工件：Playwright MCP 工具 5s 超时后底层 click 重试存活（僵尸点击）+ 共享浏览器实例干扰窗口；**非产品问题**——前端确认仅按钮 onClick 可触发（ChatPage.tsx resolveConfirm）、后端要求显式 POST+绑定 token（#112 正是合法 POST，参数金额=本人拟发内容，支出在计划内）。路径②③与 cancel 改用「snapshot 取新 ref→核 enabled→点击」纪律执行，费用闸显式确认行为干净复证。

④ P3 观察项（非 0048 引入）：job 详情 `created_at`（本地时区 15:18:07）与 `completed_at`（UTC 07:19:18）时区口径不一，沿用 listing 既有字段序列化；建议另开 issue 归 dev。
