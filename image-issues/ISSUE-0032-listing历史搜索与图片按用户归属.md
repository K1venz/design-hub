## 背景 / 需求
用户在 listing 历史页提出两点（前端转派开发）：

### 需求 1 · 历史「搜索」（P2 增强）
- `GET /listing/jobs` 增加**可选搜索参数**（如 `q` / `keyword`）：对**本人**任务按 `prompt` /
  `platform`（如有商品名字段亦可）模糊匹配，与现有 `limit/offset` 分页叠加。
- 仍按 JWT 身份隔离（只搜自己的），时间倒序。
- 前端配合：历史列表加搜索框，拿到 `q` 契约后联调（前端改动小，等后端）。

### 需求 2 · 图片「和用户对应」（P1，访问隔离）
- **现状**：ISSUE-0029 把 `/img/<sha>.png` 设为 **nginx 公开读、不鉴权**（当时定"图无安全顾虑"，
  靠随机 sha 文件名遮挡）；`/uploads/{id}` 代理也未按用户校验。→ **任何人凭 url 可访问任意用户的图**。
- **新要求**：图片（上传产品图 + AI 生成图）**与用户绑定**，访问**按用户隔离**——用户只能访问自己的图，
  他人即便拿到 url 也不可见（403/404）。这是对 ISSUE-0029「暂不鉴权」的**收紧**（用户改主意，要隐私隔离）。

## 期望 vs 实际
- 期望：① 历史可按关键词搜本人任务；② 每张图归属其用户，跨用户访问被拒。
- 实际：① 无搜索参数，只能翻页；② 图全公开，URL 即权限，无用户隔离。

## 环境 / 上下文 · 设计提示（约束需后端权衡，前端配合）
**关键约束**：原生 `<img src>` **不能带 Bearer 头**（同 ISSUE-0011 的 SSE 问题）。
所以"把 /img 直接改成 Bearer 鉴权"会导致前端图**显示不出来**。后端需选可落地的隔离方案，例如：
- **方案 A 签名 url**：`/listing/jobs` 返回的图 url 带**短时效签名 token**（query），图片服务校验 token+归属。
  前端零额外改动（拿到的 url 已含 token，直接 `<img src>`）。← 前端最省、推荐优先评估。
- **方案 B 同源 cookie 会话**：图片走同源带 cookie 的代理端点校验用户。需登录态 cookie 方案。
- **方案 C 每用户命名空间 + 代理校验**：路径含 user 维度，代理按 JWT/会话校验归属。

具体取舍 + 是否波及海报流/历史回放 + DB 是否要记 image↔user 归属，由**开发/PM 定**；
定下契约（尤其图 url 形态）后知会前端。**前端现状**：历史/详情直接用后端返回的图 url 做 `<img>`，
若走方案 A（签名 url），前端无需改结构、仅天然生效。
