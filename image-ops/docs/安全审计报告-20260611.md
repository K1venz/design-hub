## A · 服务器攻击面

### A① 对外端口
- **现状**：外网实测 22/80/443 OPEN、**3306/8000 filtered**（云安全组挡住）。但宿主机 `ss` 显示 **mysql docker-proxy bind `0.0.0.0:3306`**、mysql 容器 `bind_address=*`——3306 在宿主机层公网 bind，仅靠**火山安全组**兜底。本地 `ufw inactive`、`iptables INPUT 空` → **防护 100% 依赖云安全组单层**。
- **风险 P2**：ISSUE-0036 仍未修（3306 公网 bind）。当前外网不可达（安全组挡），但同 VPC 主机/安全组误改即暴露 MySQL；且单层防护无纵深。
- **建议**：mysql 端口映射改 `127.0.0.1:3306:3306`（或移除 publish，仅 docker 网络互通，api 不受影响）；本地加 ufw 兜底（仅放 22/80/443）。

### A② nginx
- **现状**：① `server: nginx/1.27.5`（server_tokens 默认 on，版本泄漏）② **零安全响应头**（无 HSTS/CSP/X-Frame-Options/X-Content-Type-Options/Referrer-Policy）③ **`/docs`/`/redoc`/`/openapi.json`/`/metrics` 全公网 200**。
- **风险**：`/metrics`(Prometheus) 公网 = 内部指标/请求量泄漏 **P1**；`/docs`+`/openapi.json` 公网 = 全 API 契约暴露给攻击者画攻击面 **P2**；无安全头 = 点击劫持/MIME 嗅探/降级 **P2**；版本泄漏 **P3**。
- **建议**：`server_tokens off` + 加安全响应头一组；`/docs`/`/redoc`/`/openapi.json`/`/metrics` 限内网/加 basic auth/上线前关闭（/metrics 尤其只给 Prometheus 内网）。

### A③ SSH
- **现状**：`PermitRootLogin yes`、`PasswordAuthentication yes`（50-cloud-init.conf 开着密码登录）、**fail2ban 未装**。root authorized_keys 仅 1 个（部署密钥，good）。
- **风险 P1**：root + 密码 SSH 对公网开 = 字典爆破面，无 fail2ban 无锁定。
- **建议**：`PermitRootLogin prohibit-password`（或 no + 建 sudo 运维用户）、`PasswordAuthentication no`（已有密钥登录、密码登录纯风险）、装 fail2ban。⚠️ 改 SSH 前确认密钥登录可用、别把自己锁外面。

### A④ 应用层防滥用
- **现状**：nginx 无 `limit_req/limit_conn`、应用无频控；**实测连发 3 次 `/api/auth/register` 全 200**。配额仅"内部三红线"(¥200/月/用户≈500张，对 toC=没闸)。
- **风险 P1（=gate 7.C，已知，此处量化）**：脚本可批量注册 + 每号薅出图额度 = 直接刷 gpt 成本（资损）。toC 上线前必堵。
- **建议**：注册加验证码/邮箱验证；nginx `limit_req` 对 /auth/* 和 /listing/* 限频；新号免费额度 + 风控（7.D 积分制配套）。

### A⑤ Docker
- **现状**：4 容器**全 root 跑**（Config.User 空）；✅ **无容器挂 docker.sock**（好）；镜像=本地 build(api) + 官方(mysql/nginx)。
- **风险 P2**：容器逃逸即 root。
- **建议**：Dockerfile 加非 root USER（api 容器优先）；mysql/nginx 用官方非 root 变体或 user 指令。非紧急。

### A⑥ 防火墙/安全组
- **现状**：宿主机本地防火墙空（ufw inactive/iptables 空）；有效规则=火山安全组（云侧，SSH 读不到，由端口实测反推：入站放 22/80/443、挡 3306/8000）。
- **风险 P2**：单层（仅云安全组），无主机纵深；安全组规则历史教训=编辑易覆盖（曾覆盖丢 22）。
- **建议**：主机加 ufw 兜底纵深；安全组规则导出存档、变更走评审。

## B · CI 安全（self-hosted runner + deploy.yml）

### B① 双部署 + 无备份迁移（🔴 最重磅）
- **现状（gh run 历史 + deploy.sh 实查）**：`deploy.yml` = **push 到 main 自动触发**、runner **active**（自 06-05 跑、Runner.Listener 活）。gh run 历史确认套图(27263)/0042(27272)/复刻(27278) **每次 push 都 success 自动部署**。而这几轮 ops 同时在**手动 rsync+deploy** → **每轮部署了两次**（手动 + CI）。`deploy.sh` 内含 `docker compose run --rm api alembic upgrade head`（**跑迁移**）+ build + up -d，**但无 mysqldump 备份**。
- **风险 P1**：① 双部署=冗余 + prod"真相源"歧义（我 rsync 的 vs CI 从 GitHub checkout build 的，前端 dist 尤其：CI 用 main 重 build、覆盖我 rsync 的 dist）；② **CI 跑破坏性迁移不备份**——本轮 0041 删拍拍熊那种 DELETE 迁移，若 CI 先于我手动备份部署跑到，**无备份兜底**（本次靠"我先部署带备份、push 在后"的时序运气，非设计保证）；③ 迁移幂等所以没炸，但这是运气不是机制。
- **建议（用户/coordinator 决策）**：**定唯一部署路径**——(a) CI-only：停 ops 手动部署、但 deploy.sh **必须先加 mysqldump 备份**再 alembic；(b) manual-only：deploy.yml 去掉 push 触发、仅留 workflow_dispatch，ops 手动部署(现行带备份纪律)。无论哪条，**deploy.sh 迁移前加备份**是底线。

### B② runner 在 prod = RCE 面（🔴 P1）
- **现状**：runner 跑在生产机、root 权限的 systemd 服务、构建链含 `npm ci --legacy-peer-deps`（拉第三方依赖）。
- **风险 P1**：依赖投毒 / 仓库写权限失守 → runner 在 prod 执行任意代码 = 生产 RCE。private 仓 + 可信提交人降低概率，但攻击面真实。
- **建议**：runner 隔离（独立构建机/容器、非生产机）；或至少 runner 跑专用低权限用户(非 root)、限制其只能 deploy 不能碰别的。

### B③ 无门禁（🔴 P1）
- **现状**：deploy.yml = checkout→setup-node→npm build→rsync→deploy.sh。**无 lint/test/gitleaks 前置**，第三方 action（checkout@v4/setup-node@v4）钉的是 major tag 非 commit SHA。
- **风险 P1**：坏码/泄密直接上 prod（本轮敏感扫描靠**本地 gitleaks 人工**+用户手 push，无自动门禁）。
- **建议**：deploy 前加 job：ruff + pytest + gitleaks，全过才 deploy；third-party action 钉 commit SHA；加分支保护(PR review/必过 CI)。
- ✅ **一个正面**：deploy.yml 不用任何 secret（本地 runner、无跨网 SSH 密钥），GITHUB_TOKEN 未显式用——secret 泄漏面小。

## 总结·建议优先级
1. **B① 部署路径单一化 + deploy.sh 迁移前备份**（最优先，资损/数据安全）
2. **A④ 防滥用** + **A③ SSH 加固**（toC 上线硬 gate，与 7.C 并）
3. **A② /metrics·/docs 收口 + nginx 安全头**、**B② runner 隔离**、**B③ CI 门禁**
4. A① mysql 3306 收 bind(ISSUE-0036)、A⑤ 容器非 root、A⑥ 主机 ufw 纵深
> 全部"建议不做"，等用户看完拍要不要修 + 排期。
