# 全局生图质量约束与 Chat 4K 路由设计

日期：2026-07-25  
状态：已实现，待最终验收

## 1. 背景与目标

当前项目的 Chat、商品图、商品套图、爆款复刻和二次编辑会先组合各自的业务提示词，
再调用 GPT Image Provider。各入口已有产品保真、图型、编辑模式和用户自由文本等规则，
但缺少一段在所有真实生图请求中稳定生效的全局质量底线。

本次同时引入两项相关能力：

1. 所有真实生图 API 请求统一附带一段全品类质量提示词，只提升真实性、文字准确度和
   细节完成度，不改变用户明确要求。
2. Chat 在用户明确要求 4K 时选择 `gpt-image-2-4k`；普通请求继续使用
   `gpt-image-2`。

目标是：

- 所有生图入口都不遗漏全局质量约束。
- 全局约束兼容商品摄影、人物、动物、Logo、海报、插画、3D 和其他品类。
- 只有用户明确要求 4K 时才产生 4K 成本和固定 16:9 输出。
- 普通和 4K 模型使用真实、独立的价格确认与账本记录。
- 三把 API Key 只存在于环境密钥配置中，并由两个模型共享轮换。

## 2. 已确认的上游能力

官方文档：
[APINebula image2-4k 分组](https://docs.apinebula.ai/docs/advanced/image/image2-4k)

文档与 2026-07-25 授权实测共同确认：

- 4K 请求模型名为 `gpt-image-2-4k`。
- 支持 `/images/generations` 和 `/images/edits`。
- 唯一支持尺寸为 `3840x2160`，即 16:9 横版。
- 文档建议最长请求超时为 1800 秒。
- 参考图编辑支持 `input_fidelity=high`。
- 一次最小探测使用 `n=1`、`quality=high`，45.81 秒返回 HTTP 200 和有效图片 URL。
- 中转账单将请求计费模型记录为 `gpt-image-2-4k`，底层实际模型显示为
  `gpt-image-2`；这是中转站内部路由信息，不改变本系统的模型选择语义。
- 探测账单价格为 ¥0.18/次。

本系统采用用户确认的展示与扣费价格：

| 模型 | 单价 | 尺寸 |
|---|---:|---|
| `gpt-image-2` | ¥0.05/张 | 现有 1:1、3:4、4:3、9:16、16:9 |
| `gpt-image-2-4k` | ¥0.18/张 | 固定 3840×2160（16:9） |

## 3. 非目标

- 本次不在商品套图、爆款复刻等独立页面增加 4K 开关。
- 本次不支持 4K 方图、竖图、3:4 或 4:3；上游不具备这些尺寸。
- 不根据“高清”“超清”“高分辨率”等模糊表达自动升级 4K。
- 不把全局提示词保存进用户消息、任务历史或数据库 prompt 字段。
- 不把所选模型持久化到 `listing_job`，不向任务历史 API 增加模型字段。
- 不为本需求新增数据库迁移；生产 MySQL schema 保持不变。
- 不为全局提示词建设后台在线编辑器或版本管理界面。
- 不在代码、迁移、文档、测试夹具或日志中保存 API Key。
- 4K 失败后不静默降级为普通模型。

## 4. 总体架构

### 4.1 全局质量提示词

GPT Images API 没有独立的 `system` 消息角色。系统在真实 Provider 发出请求前，将三个
部分组合成最终线上的 `prompt`：

```text
【全局真实性与细节质量约束】
固定全局提示词

【本次生图要求】
现有业务提示词与用户要求

【需要避免】
现有 negative prompt（非空时）
```

注入点放在 GPT Image Provider 共用的最终提示词组装边界，而不是分别放在
Chat、套图、复刻和编辑用例中。这样：

- 文生图和参考图编辑都覆盖。
- 两个运行时模型的同步 Images API generation/edit 都覆盖。
- 新增业务入口只要使用现有 GPT Image Provider，就自动继承规则。
- 全局提示词只注入一次。
- 数据库仍保存干净的业务 prompt，历史展示和重放语义不被固定文本污染。

全局提示词属于应用级质量策略，应放在独立模块中；Provider 共用组装函数引用该策略，
避免把长文案散落在 HTTP 适配器或多个业务用例里。

### 4.2 双模型注册

领域模型新增 `gpt-image-2-4k`，并与普通模型分别注册：

- 普通与 4K 模型都使用同步 OpenAI 兼容 Images API：文生图调用
  `/v1/images/generations`，带参考图调用 `/v1/images/edits`。
- 运行时连接协议必须声明为 `openai_compat_image`；默认连接声明其他协议时启动
  fail-fast，不静默切回异步任务协议。
- 4K Provider 固定模型名 `gpt-image-2-4k`、固定尺寸 `3840x2160`，请求超时
  1800 秒。
- 现有 Nginx `proxy_read_timeout` 和 `proxy_send_timeout` 均为 3600 秒，无需因
  4K 调整网关超时。

两个 Provider 使用同一个共享 API Key 轮换器。轮换器负责：

- 每个新逻辑请求领取下一个 Key。
- 429、超时、传输错误和 5xx 重试时切换下一把 Key。
- 普通和 4K 请求共享同一游标，避免各 Provider 都从第一把 Key 开始形成热点。
- 错误信息和日志不包含 Key 明文。

三把 Key 通过现有环境变量的逗号分隔密钥池注入，本地和生产分别安全更新。

连接解析只执行一次：沿用当前普通模型的兼容默认连接配置，取得中转地址、普通上游模型名
和三 Key 密钥池。普通 Provider 使用解析出的模型名，4K Provider 固定使用
`gpt-image-2-4k`；两者复用同一同步 Images API 连接和同一个 `ApiKeyPool`。这样不复制
连接配置，也不把 Key 分散到第二套环境变量中。

## 5. 全局真实性与细节质量提示词

最终固定文本如下：

```text
【全局真实性与细节质量约束】

本约束只用于提高画面的真实性、文字准确度与细节完成度，不得改变本次任务明确指定的主体、数量、构图、画幅比例、颜色、场景、文案、参考图角色和艺术风格。

严格遵循本次任务对参考图角色的定义。被指定为产品图、主体图或编辑源图的内容，应保持其外形、结构、比例、材质、颜色、图案、包装、已有文字与 Logo 一致，除非用户明确要求修改。被指定为风格、构图或场景参考的图片，只学习任务明确要求的视觉特征，不得擅自复制其中的产品、人物、文字、Logo 或品牌元素。

对于照片、商品图和其他物理场景，主体结构、比例、透视、连接关系和边缘必须自然准确；产品、人物、动物及其他物体不得出现融合、重复、残缺、悬浮、错位、异常肢体或不合理变形。材质应符合真实物理特征，保留合理纹理、表面层次和细微自然差异，避免塑料感、蜡感、过度磨皮、过度锐化、虚假反光、整面高光和 AI 涂抹痕迹。

对于存在真实光照的画面，光源方向必须统一，曝光自然，高光不过曝，暗部保留细节。只保留真实接触阴影和符合主光源方向的自然投影；禁止多重阴影、无来源阴影、悬浮阴影、重复影子、过重黑边和不自然的棚拍假阴影。对于 Logo、扁平插画、图标、纯平面设计或透明底素材，不得擅自添加写实光影、立体效果或投影。

只有本次任务指定需要保留的已有文字，或用户明确要求生成的文案，才允许出现在画面中。指定文字必须一字不增、一字不减、一字不改，清晰可读，字形完整，间距与排版自然；禁止错字、乱码、重复文字、变形文字和伪文字。未经明确要求，不得新增营销词、标签、Logo、水印、装饰字符或其他文字。

用户未指定非写实风格时，物理场景默认呈现自然可信的真实质感。用户明确指定插画、卡通、3D、油画、平面设计等风格时，只提升该风格内部的结构、材质、文字和光影可信度，不强制改成照片，不额外改变其视觉语言。

主体与背景的清晰度、色温、颗粒、景深和光照关系应保持协调；边缘融合自然，避免抠图白边、异常光晕、锯齿、穿帮、拼接痕迹、局部分辨率不一致和局部风格突变。上述要求仅在对应画面类型适用时执行，不得为了套用质量规则而添加用户没有要求的内容。
```

这版文本刻意处理三个全品类冲突：

1. 非摄影任务不被强制转成照片。
2. 参考图按产品、编辑源和风格参考的角色分别约束，避免复刻时复制参考商品或品牌。
3. 扁平视觉和透明素材不被强制增加写实阴影。

## 6. Chat 4K 意图与比例规则

4K 只在本轮消息同时满足“存在生图/改图意图”和“明确正向表达 4K”时触发。

正向示例包括：

- `4K`
- `4 k`
- `生成4K`
- `做成 4K 图`
- `超高清4K`
- `3840×2160`
- `3840x2160`

以下表达不触发：

- `高清`
- `超清`
- `高分辨率`
- `清晰一点`
- `不要4K`
- `不要生成 4K`
- `不需要做成 4K`
- `不用改成 4K`
- `别用 4K`
- `不是 4K`
- `无需 4 K`
- 单纯讨论 4K 能力但没有本轮生图/改图意图

解析采用确定性、有顺序的分句状态机，不依赖文本 LLM 是否主动选择 4K：

- 按标点和明确转折词依次读取分句。
- 每个包含 4K token 的分句产生一次“要求 4K”或“明确取消 4K”决策。
- 最后一个明确决策覆盖之前的决策，确保“先要求、后取消”不会意外调用高价模型，
  “先取消草稿、后要求成品”仍能正确调用 4K。
- 比例只从最后一个明确决策所在分句及其后续文本提取；被覆盖分句中的旧比例不参与最终
  冲突判断。若没有明确 4K 决策，则普通模型仍读取整条消息的比例。

比例决策：

1. 4K 且未写比例：使用 16:9、3840×2160。
2. 4K 且明确 16:9 或 3840×2160：正常继续。
3. 4K 且明确 1:1、3:4、4:3 或 9:16：不创建费用确认、不启动任务，提示用户选择：
   - 继续生成 4K 16:9 横版；或
   - 使用普通模型按指定比例生成。
4. 4K 且明确写出其他不支持比例（如 2:3）：沿用现有“五种支持比例”说明，不误报为
   “取消 4K 即可保留该比例”。
5. 未触发 4K：沿用现有普通模型比例优先级：
   - 用户明确比例；
   - “横版”等语义映射 4:3；
   - 第一张上传图比例；
   - 兜底 1:1。

二次编辑同样只读取本轮编辑指令。用户选择一张 4K 或普通结果继续编辑，并不自动延续 4K；
只有本轮再次明确写出 4K 才选择 4K Provider。这样避免后续小修改在用户不知情时持续产生
4K 费用。

## 7. Chat 能力文案

新对话欢迎语更新为：

> 我可以基于你上传的图片制作全品类主图、场景图、卖点图、海报、Logo/品牌视觉，
> 也支持爆款复刻和连续编辑。普通出图支持多种比例；如需 4K，请在需求中明确写出
> “4K”，4K 当前仅支持 16:9 横版。上传至少 1 张图片，再告诉我想做什么即可。

费用确认卡使用被选运行时 Provider 的固定价格：

- 普通模型显示 ¥0.05/张。
- 4K 模型显示 ¥0.18/张。
- 多张请求按对应模型单价乘以张数。
- 4K Chat 单次最多 3 张；超过时在 `tool_call`、费用确认、pending 和 job 之前返回：
  `4K 单次最多生成 3 张，请将本次数量调整为 1–3 张；如需更多，请分批生成。`

4K 比例冲突文案不暴露内部字段名或技术模型名，只说明能力限制和两个可选方向。

## 8. 数据与配置

### 8.1 模型配置

运行时固定价格只来自 Provider registry：

- `gpt-image-2`：`unit_cost=0.05`
- `gpt-image-2-4k`：`unit_cost=0.18`

持久 `model_config.unit_cost` 不参与这两个固定价 Provider 的费用确认、额度报价或扣费；
已有数据库中的旧 `0.40` 不得覆盖运行时价格。启动默认配置只 seed 普通模型，不新增
`gpt-image-2-4k` 配置行，也不使用 Alembic 数据迁移写入价格。

模型只在运行时由 Chat 渲染决策产生，并保存在费用确认的 `PendingAction` 快照中；用户
确认后，该快照显式传递到 launcher、尺寸校验、Provider 和当次费用流程。模型不写入
`listing_job`，任务历史 summary/detail API 不增加模型字段。生产使用 MySQL，但本需求
不改变任何数据库 schema、不新增迁移，Alembic head 保持 `f3a4b5c6d7e8`。

4K 配置行缺失表示没有显式覆盖，不禁用 registry 中已注册的 4K 能力；若该行存在且被
管理员停用，Chat 返回“4K 当前不可用”，且不创建费用确认或任务。费用卡发出后、用户
确认前还会重查 registry 与显式启用状态，期间被停用的模型不得启动。取消同样必须匹配
当前 confirm token；陈旧或错误 token 不得清除有效 pending。

## 9. 错误处理与退款

- 4K 比例冲突是确定性业务冲突，必须在创建任务和费用确认前返回说明。
- 4K API 的 400、401、403、422 等确定性 4xx 继续 fail-fast，不换 Key、不降级。
- 429、传输异常和 5xx 可在 4K 专用总墙钟预算内换 Key 重试。
- 4K HTTP 客户端超时与总重试墙钟均设为 1800 秒：早期出现的瞬时错误仍可换 Key；
  如果一次请求已耗尽 1800 秒，则不再启动第二个长请求。
- 4K 最终失败后不调用普通模型兜底。
- 任务失败沿用现有 CostGuard 回正/退款路径，确保没有成功图片就不产生最终扣款。
- 任务在预扣后收到 `asyncio.CancelledError` 时，生成/复刻/编辑服务先退款，命令层先把
  job 终结为失败并发送 `TASK_FAILED`，随后重新抛出取消；不得留下扣款或“生成中”僵尸。
- 用户取消费用确认时不调用任一图片 API。
- Chat SSE 等待事件期间每 20 秒发送一次 `: keep-alive` comment，避免长 4K 请求被代理
  当作空闲连接关闭；心跳不取消或重建正在等待的上游迭代。
- 启动僵尸任务 reaper 使用 45 分钟阈值，覆盖最长 4K 三张批次及余量。该无 schema
  方案的明确取舍是：真实长任务不被误杀，但进程崩溃留下的死任务最多比旧 15 分钟阈值
  晚约 30 分钟恢复。

## 10. 测试与验收

### 10.1 单元与契约测试

- 全局提示词位于业务 prompt 之前，negative prompt 位于末尾。
- 空 negative prompt 不产生空标题或重复片段。
- 普通与 4K 同步 generation/edit 都只注入一次全局提示词。
- 全局提示词不写回任务持久化 prompt。
- 4K 正向、模糊、否定和讨论表达解析正确。
- 4K 与四种不支持比例的冲突均在计费前阻断。
- 4K 默认 16:9；普通模型继续通过现有五比例测试。
- Chat 普通费用确认显示 ¥0.05，4K 显示 ¥0.18。
- 旧数据库价格不能覆盖固定运行时价格，且 4K 无默认 seed 行。
- 费用确认快照和确认后的 launcher 调用分别携带本轮实际选择的模型。
- `listing_job` 与任务历史 API schema 不新增模型字段，Alembic head 保持不变。
- 继续编辑只有本轮再次明确 4K 才升级。
- 两个 Provider 共用三 Key 轮换器，重试不泄露 Key。
- 4K Provider 发送固定模型、尺寸、数量、质量，以及 1800 秒客户端/总墙钟配置。
- 4K Chat 超过 3 张使用固定用户文案并在费用卡前阻断。
- Chat 长等待产生 20 秒 SSE comment 心跳；预扣后取消完成退款和失败终态。
- 启动 reaper 使用 45 分钟阈值，30 分钟的在飞任务不被误扫。
- Chat 新对话欢迎语包含 4K 明示条件与 16:9 限制。
