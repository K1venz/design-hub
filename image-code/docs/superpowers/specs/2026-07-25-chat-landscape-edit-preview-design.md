# Chat 横版比例、连续编辑与图片预览设计

## 背景

「帮我设计」Chat 已支持全品类出图、同轮保守完善需求、生成意图判断、上传首图比例继承和费用确认。
目前仍有三个连续体验缺口：

1. 用户说“横版、横图、横向构图”时，没有稳定映射到 `4:3`。
2. Chat 结果图只能下载，不能在当前对话中明确选择一张继续编辑。
3. 结果卡使用方形缩略图，无法打开按原始比例完整展示的大图预览。

底层已经具备 owner-scoped 的二次编辑链路、`edit` 工具、历史任务详情和稳定的
`image_key`。本需求复用这些能力，不新建第二套编辑 API。

## 目标

- Chat 支持 `1:1`、`3:4`、`4:3`、`9:16`、`16:9` 五种比例。
- “横版、横图、横向构图”等无数字横向表达固定采用 `4:3`。
- 用户明确输入受支持的数字比例时，数字比例覆盖横版表达和上传首图比例。
- 每张已完成的 Chat 结果图都可以被明确选为下一轮编辑底图。
- 选择底图后，用户仍需输入编辑要求并经过原有费用确认，不因点击按钮直接生图或扣费。
- 编辑结果继续提供同样的预览和继续编辑能力。
- 当前结果和历史会话结果均可打开原图比例预览。

## 非目标

- 不支持五种比例之外的任意尺寸。
- 不改变工作台、爆款复刻页和独立二次编辑页的交互。
- 不新增图片版本回滚、版本对比或图片删除。
- 不修改现有会话最多 5 个出图任务的限制；达到上限后仍提示用户新开会话。
- 不承诺局部编辑中的未修改像素完全不变；继续沿用现有 `delta`/`full` 能力边界。

## 已确认的交互

### 选择编辑底图

每张成功结果图显示“继续编辑”操作。点击后：

- Chat 不跳转页面。
- 输入框上方显示选中图片的缩略图和“正在基于此图编辑”。
- 用户可以移除选中图片，或点击另一张结果图重新选择。
- 选择动作本身不发送消息、不调用 LLM、不创建任务、不扣费。
- 用户输入编辑要求并发送后，当前选中的稳定图片标识随消息提交。
- 消息发出后清空输入区的选中态；已经提交的请求不受后续选择影响。

多图场景以用户点击的图片为唯一底图，不让 LLM 猜测“上一张”或“第二张”。没有明确选择底图时，
现有自然语言对话仍可继续，但不得凭 URL 推导或猜测 `source_image_key`。

### 连续编辑

编辑结果与普通生成结果使用同一结果卡。新结果完成并取得稳定 `image_key` 后，再次显示“继续编辑”，
因此用户可以在现有会话任务上限内逐轮迭代。每一轮都以本轮明确选择的结果图为源图，原结果和历史记录保留。

### 图片预览

点击成功结果图主体打开模态预览：

- 图片使用自身宽高比完整展示，不裁切。
- 最大尺寸受当前视口约束，桌面端和移动端都不产生页面级溢出。
- 支持关闭、下载和“继续编辑”。
- 点击遮罩或按 `Esc` 关闭。
- 从预览中点击“继续编辑”时，关闭预览并把当前图片设为输入区编辑底图。

当前 SSE 结果与历史会话中的任务详情使用同一预览组件和操作语义。

## 比例规则

### 支持集合与模型尺寸

| 业务比例 | GPT Image 2 请求尺寸 |
|---|---:|
| `1:1` | `1024x1024` |
| `3:4` | `1152x1536` |
| `4:3` | `1536x1152` |
| `9:16` | `864x1536` |
| `16:9` | `1536x864` |

`4:3` 尺寸已经通过当前中转站真实请求验证：API 接受 `1536x1152`，返回图片为
`1448x1086`，宽高比保持精确 `4:3`。服务端只依赖比例，不依赖返回像素必须等于请求像素。

### Chat 决策优先级

比例按以下固定优先级决定：

```text
受支持的明确数字比例
    > 横版/横图/横向构图等横向表达（4:3）
    > 第一张上传图片的受支持比例
    > 1:1
```

示例：

- “做一张横版主图” → `4:3`
- “做一张横版 16:9 主图” → `16:9`
- “按 3:4 出图” → `3:4`
- 未写比例、第一张上传图为 `4:3` → `4:3`
- 未写比例且首图无法识别 → `1:1`

比例决策由独立纯函数完成，输出本轮确定比例及来源。LLM 负责理解设计需求，但不能改变确定后的比例：

- `generate`/`clone` 请求统一使用本轮确定比例。
- 已选编辑底图且未要求改比例时，`edit` 不传比例，继承源图比例。
- 已选编辑底图且明确要求数字比例或横版时，使用 `full` 编辑并传入确定比例。
- 不受支持的明确比例不静默近似到其他比例，由 Chat 告知当前支持集合并请用户重选。

### 上传图识别

首图识别集合同步增加 `4:3`，继续使用 EXIF 方向校正、完整 JPEG 校验和 1% 相对误差阈值。
读取、解码或匹配失败属于现有 I/O 兜底范围，返回 `1:1`。

## 架构与数据流

### 前端状态

ChatPage 增加页面级 `selectedEditSource`：

```ts
interface ChatEditSource {
  imageKey: string
  url: string
  imageType?: string
}
```

该状态只描述尚未发送的编辑选择，不进入全局 store，也不持久化到会话转录。刷新页面后可以从历史结果卡重新选择。

结果渲染使用稳定的 `ResultSlot.imageKey` 决定是否展示“继续编辑”：

- SSE 只负责即时展示生成进度和临时 URL。
- `job_started` 保存当前 `job_id`。
- 任务详情查询按现有轮询机制取得落库后的图片和 `image_key`。
- 使用现有 `detailToResultSlots`/合并逻辑把稳定标识补入当前结果。
- 历史会话本来就通过 `job_id` 拉任务详情，因此无需新增历史接口。

生成中、失败、没有 `image_key` 的槽位不展示编辑入口。

### Chat 请求契约

`POST /chat/messages` 增加可选字段：

```json
{
  "session_id": "string | null",
  "message": "把背景改成海边，产品保持不变",
  "upload_ids": [],
  "edit_source_image_key": "stable-generated-image-key"
}
```

`edit_source_image_key` 是界面选定的编辑上下文，不拼进用户可见文本，也不作为上传附件持久化。
后端把它作为仅供本轮 LLM 使用的系统备注：

```text
[系统备注] 用户已通过界面明确选定编辑底图 source_image_key=...。
若本轮是修改该图，必须原样调用 edit；不得改用 generate，也不得猜测其他底图。
```

LLM 仍执行现有“明确生图意图才调用写工具”的判断。选中底图后，如果用户只讨论设计方案，
仍返回顾问答复，不自动调用 `edit`。

### 编辑请求

用户明确要求修改且已选择底图时：

1. Chat LLM对用户原始要求做同轮、保守的完善，不额外插入澄清轮。
2. 未要求改变整体构图或比例时，调用 `edit`，`edit_mode="delta"`，不传 `ratio`。
3. 明确要求重新设计整体画面、改变构图或比例时，调用 `edit`，`edit_mode="full"`。
4. `source_image_key` 必须等于请求中的 `edit_source_image_key`。
5. 继续经过现有参数校验、owner/父链解析、费用确认、任务事件和历史落库。

后端现有 `resolve_edit_source` 继续作为安全边界：不存在、失败图片或非本人图片统一按无权访问处理，
不会在创建任务和计费后才发现。

## 组件边界

### 后端

- `chat/ratio_intent.py`：从本轮文本和自动比例产生唯一比例决策，不依赖 LLM。
- `chat/image_ratio.py`：识别上传图的五种受支持比例。
- `chat/orchestrator.py`：注入比例决策和选中底图备注；校验 LLM 写工具参数与本轮决策一致。
- `chat/system_prompt.py`：声明五种比例、横版映射和已选底图的编辑规则。
- `listing/sizing.py`：维护业务比例到 GPT Image 2 请求尺寸的唯一映射。
- Chat interface schema/route：透传可选 `edit_source_image_key`。

### 前端

- `lib/chat.ts`：定义选中编辑源、当前任务标识及 reducer 所需纯状态变换。
- `api/chat.ts`：把可选 `editSourceImageKey` 映射到请求字段。
- `components/chat/ChatImagePreviewDialog.tsx`：只负责大图预览和下载/继续编辑事件。
- `pages/ChatPage.tsx`：管理选中态、把结果图操作连接到输入区，并在发送时提交稳定标识。

预览组件不读取网络、不拥有业务状态；图片下载继续复用现有 `downloadImage`。

## 错误处理

- 用户篡改或提交非本人 `edit_source_image_key`：沿用 owner-scoped 404 口径，不泄露图片是否存在。
- 结果详情暂未返回 `image_key`：图片可预览和下载，但编辑入口等待稳定标识后再出现。
- 任务生成失败：失败槽不提供预览或编辑；既有成功结果不被覆盖。
- 预览图片加载失败：保留关闭操作并显示“图片加载失败”，不清空聊天状态。
- 用户发送编辑要求时选中态缺失：不猜底图；LLM自然追问用户选择具体结果图。
- 不支持的明确比例：不调用生图工具、不自动改成邻近比例，返回五种支持比例。
- 网络请求失败：保留原图和历史结果，用户可以重新选择并提交。

## 测试与验收

### 后端

1. `ratio_to_size("4:3") == (1536, 1152)`，其他五种映射保持准确。
2. 首图比例识别覆盖标准和整数误差范围内的 `4:3`。
3. 比例决策覆盖明确数字、横版别名、首图继承和 `1:1` 兜底。
4. “横版 16:9”选择 `16:9`；不支持比例不会进入写工具费用闸。
5. `edit_source_image_key` 只进入本轮系统备注，不进入用户可见消息或附件记录。
6. 已选图的编辑工具调用必须使用完全相同的 `source_image_key`。
7. 编辑未改比例时保持 `delta` 且不传比例；改比例时使用 `full`。
8. 非本人或不存在图片不会创建任务或扣费。

### 前端

1. Chat 请求只在选择编辑底图时携带 `edit_source_image_key`。
2. 点击“继续编辑”设置唯一选中态；切换、移除和发送后清空行为正确。
3. 选择图片不会直接触发 Chat 请求或费用确认。
4. 当前任务详情补齐 `imageKey` 后出现编辑入口。
5. 历史会话恢复后仍能预览并选择结果图。
6. 点击图片、按 `Esc` 和点击遮罩符合预览开关预期。
7. 预览按原比例完整展示，并提供下载和继续编辑。
8. 编辑结果再次具备预览和继续编辑入口。
