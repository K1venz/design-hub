# 管理后台设计

- 日期：2026-07-30
- 状态：已确认，待实现
- 范围：管理后台总览、用户管理、出图审核、模型调用统计、模型配置整合、管理员操作记录

## 1. 背景与目标

项目已经具备两项分散的管理能力：

- 用户列表与“用户 / 管理者”角色调整；
- 出图模型配置、启停、单价和默认渠道切换。

现阶段缺少统一的管理入口，也无法跨用户查看出图、执行内容合规处置或核对真实上游调用。尤其是：

- `listing_job`、`generation_item` 和 `listing_image` 能说明业务任务、图片和平台核算成本，但不能准确还原每次上游请求与重试；
- GPT Image 2 的调用次数没有独立明细；
- 豆包 Chat 当前没有保存上游返回的输入、输出和总 token；
- 管理员处理违规图片、停用用户或修改模型时没有统一审计记录。

本次目标是增加一套克制的管理后台，使管理者能够：

1. 查看平台用户、任务、全部生成结果图和模型调用情况；
2. 对生成结果执行“先出图、后审核”的合规处置；
3. 准确统计 GPT Image 2 的实际调用次数和豆包 Chat 的调用次数及 token；
4. 停用或恢复用户；
5. 追溯关键管理员操作。

本次不建设完整运营平台，不引入自动审核、多级审批、外部 BI 或复杂权限系统。

## 2. 已确认的产品决策

### 2.1 管理入口

普通产品导航只保留一个“管理后台”入口。管理者进入后使用独立后台布局和侧边导航，不再把“用户管理”和“模型配置”作为两个零散入口展示。

### 2.2 图片审核

- 新生成图片默认正常并直接交付，不增加用户等待；
- 管理员能够查看全部用户生成结果；
- 管理员可标记违规并禁止普通用户继续预览、下载或作为二次编辑源图使用；
- 审核入口、违规原因、内部备注和处理记录仅对管理员可见；
- 普通用户只看到“该图片暂不可用”，不看到审核原因或后台状态；
- 管理员可恢复图片，第一版不物理删除对象；
- 平台内的屏蔽立即生效；屏蔽前已经签发并被复制的临时对象链接，最长可能继续有效约一小时，之后自然失效。

### 2.3 模型调用统计

GPT Image 2 以调用次数为核心：

- 每次实际发往上游的 `images/generations` 或 `images/edits` 请求计一次；
- 重试请求单独计数；
- 异步任务状态轮询、结果图片 CDN 下载不计为模型调用；
- token 能从响应稳定取得时顺带保存，拿不到时允许为空，不影响核心统计。

豆包 Chat 同时记录：

- 每次实际 Chat Completion 请求；
- 输入 token；
- 输出 token；
- 总 token。

一条用户消息可能触发多轮模型调用，每轮都独立计数。历史调用没有可靠明细，不做反推或伪造补数；新调用记录从本版本上线后开始。

APINebula 的 GPT Image 2 响应包含可选的 `usage`，火山方舟流式 Chat 在请求带 `stream_options: {"include_usage": true}` 时会在末尾返回用量。本设计直接采集上游事实，不用本地 tokenizer 估算。

参考：

- [APINebula GPT Image 2 1K 接口文档](https://docs.apinebula.ai/docs/advanced/image/gpt-image-2-1k/)
- [火山方舟 Chat Completions 接口文档](https://api.volcengine.com/api-docs/view?action=ChatCompletions&serviceCode=ark&version=2024-01-01)

### 2.4 用户状态

- 所有现有用户和新用户默认启用；
- 管理员可以停用或恢复其他用户；
- 停用用户后，其现有 JWT 在下一次受保护请求时失效；
- 管理员不能停用自己；
- 最后一个正常启用的管理者不能被停用或降级；
- 不删除用户及其历史图片、任务和调用记录。

## 3. 页面与交互

### 3.1 后台总览

支持今日、最近 7 天、最近 30 天和自定义时间范围，默认最近 7 天。

核心指标：

- 注册用户数与产生业务活动的用户数；
- 出图任务数、成功结果图数；
- GPT Image 2 调用次数、成功数、失败数、结果不确定数、重试数；
- 豆包 Chat 调用次数、输入 token、输出 token、总 token；
- 平台核算出图成本；
- 平均调用耗时和失败率。

页面同时展示：

- 按模型的调用趋势；
- 最近失败或结果不确定的调用；
- 最近被屏蔽的图片；
- 跳转到对应用户、任务、图片或调用明细的入口。

“平台核算成本”来源于现有模型配置单价和成功结果成本，不宣称等于中转站最终账单。

### 3.2 用户管理

用户列表采用服务端分页，支持按邮箱、姓名、角色和启用状态筛选。每行展示：

- 邮箱、姓名、角色、启用状态；
- 注册时间、最近业务活动时间；
- 出图任务数、成功图片数；
- GPT Image 2 调用次数；
- 豆包调用次数及总 token；
- 平台核算成本。

最近业务活动时间取该用户最新任务、Chat 会话或模型调用的最大时间，不在每个鉴权请求上更新用户表，避免无意义写放大。

用户详情复用同一后台信息架构，展示该用户的任务、图片和调用记录，不另建一套重复页面。

用户动作：

- 调整角色；
- 停用账号，必须填写内部原因；
- 恢复账号。

第一版不提供删除账号、重置密码、批量封禁或“以用户身份登录”。

### 3.3 出图管理

提供两种查看方式：

- 任务列表：适合排查一次业务提交及其多张结果；
- 图片网格：适合合规巡检和全量预览。

筛选项：

- 用户；
- 时间范围；
- 模型；
- 功能类型：商品套图、爆款复刻、二次编辑、换背景；
- 任务或图片状态；
- 审核状态。

任务详情展示：

- 用户和任务时间；
- 输入商品图、参考图；
- 全部结果图；
- 用户提示词和最终出图提示词；
- 功能类型、比例、尺寸、质量；
- 模型、平台核算成本；
- 关联的实际模型调用、重试、耗时和错误。

普通用户的 owner 隔离逻辑保持不变；管理员使用独立查询能力跨用户读取。输入图只在任务详情按需预览，不进入结果图片审核状态机。

### 3.4 图片审核

图片审核状态只有：

- `normal`：正常；
- `blocked`：已屏蔽。

处理流程：

```text
normal --标记违规--> blocked
blocked --恢复------> normal
```

标记违规必须选择原因：

- 色情低俗；
- 暴力血腥；
- 违法内容；
- 侵权仿冒；
- 其他。

可填写内部备注。重复屏蔽或重复恢复返回冲突，不静默成功。

屏蔽后，所有普通用户入口统一拒绝该图：

- 历史列表和详情不再签发可用预览地址；
- Chat 历史结果不再签发可用预览地址；
- 下载入口不可用；
- 反推提示词不可读取该结果图；
- 二次编辑和换背景不能再把它作为源图。

管理员详情仍可按管理者权限获得临时预览地址，以便复核和恢复。

### 3.5 API 用量

分为汇总和调用明细。

汇总按时间、模型、供应商和调用类型聚合：

- 调用次数；
- 成功、失败、结果不确定和重试次数；
- 成功率；
- 平均耗时；
- GPT Image 2 生成图片数和平台核算成本；
- 豆包输入、输出和总 token。

调用明细展示：

- 用户；
- 供应商、模型；
- 调用类型；
- 是否重试及尝试序号；
- 状态、耗时和安全错误摘要；
- token；
- 关联任务、图片或 Chat 会话。

不展示 API Key、Authorization 头、完整上游 URL 查询参数或敏感响应体。完整提示词不复制到调用记录；管理员需要时通过关联业务记录查看。

### 3.6 模型配置

现有模型配置能力迁入统一后台，功能语义不变：

- 新增和修改出图渠道；
- 启停；
- 切换默认渠道；
- 配置平台核算单价；
- 仅显示密钥环境变量名称，不显示真实密钥。

模型配置的新增、修改、启停、默认切换和删除都写管理员操作记录。

### 3.7 管理员操作记录

记录：

- 用户角色修改；
- 用户停用与恢复；
- 图片屏蔽与恢复；
- 模型配置新增、修改、启停、默认切换与删除。

每条记录包含：

- 操作者；
- 动作；
- 目标类型和目标标识；
- 安全的修改前后快照；
- 内部原因或备注；
- 操作时间。

操作记录不保存密码、JWT、API Key、完整提示词或图片字节。

## 4. 数据设计

### 4.1 `app_user` 扩展

新增：

- `enabled`：非空布尔值，历史与新用户默认 `true`；
- `disabled_at`：可空；
- `disabled_by`：可空，管理员用户 ID；
- `disabled_reason`：可空，仅管理员可见。

角色和启用状态都以数据库当前值为准，不再信任 JWT 中可能已经过期的角色快照。

### 4.2 `listing_image` 审核字段

新增：

- `moderation_status`：`normal | blocked`，历史与新图片默认 `normal`；
- `moderation_reason`：可空；
- `moderation_note`：可空；
- `moderated_by`：可空；
- `moderated_at`：可空。

图片对象本身不移动、不删除，恢复操作只修改审核状态和处理信息。

### 4.3 `model_call` 新表

每行代表一次准备发送给上游的实际模型请求。

主要字段：

- 唯一调用 ID；
- `user_id`；
- `provider`、`model`；
- `modality`：`image | chat`；
- `operation_type`：`image_generation | image_edit | chat_completion | reverse_prompt`；
- 关联的 `job_id`、`generation_item_id`、`chat_session_id`，按调用场景允许为空；
- `attempt_no`，大于 1 即重试；
- `status`：`started | succeeded | failed | uncertain | interrupted`；
- 上游请求 ID，可空；
- `input_tokens`、`output_tokens`、`total_tokens`，可空；
- GPT Image 输入文本、输入图片、输出图片 token 明细，可空；
- 安全错误码和截断后的错误摘要；
- 开始时间、完成时间、耗时；
- 成功图片调用的平台核算成本，可空。

调用记录在发出网络请求前创建。只有创建成功才允许调用上游，避免产生完全无记录的请求。收到响应或明确网络错误后更新状态；连接被取消时更新为 `interrupted`。进程在结果落库前崩溃时无法再写终态，因此管理查询把超过对应模型最大调用墙钟仍为 `started` 的记录显示为“结果不确定”，不伪装为成功或失败，也不需要后台定时修表。

同步 GPT Image Provider 的每次 POST 尝试都记录；异步 Provider 只记录提交 POST，不记录轮询 GET。豆包请求开启流式 usage，并正确处理最后一个 `choices` 为空但 `usage` 存在的 chunk。

### 4.4 `admin_audit_log` 新表

主要字段：

- 唯一记录 ID；
- `actor_user_id`；
- `action`；
- `target_type`、`target_id`；
- 安全的 `before`、`after` JSON；
- `reason`；
- `created_at`。

管理员业务修改和对应审计记录必须在同一数据库事务中提交。审计写入失败时，管理员修改整体失败，不能出现有修改但无审计的状态。

## 5. 服务端边界

### 5.1 权限

所有 `/admin/*` 路由继续统一挂管理者依赖。鉴权流程调整为：

1. 验证 JWT 签名与有效期；
2. 用 token 中的用户 ID 查询当前用户；
3. 用户不存在或已停用时返回 401；
4. 使用数据库中的最新角色执行 403 权限判断。

普通 Bearer 鉴权和 SSE query token 鉴权使用同一用户状态检查。

### 5.2 管理查询

新增独立的管理员查询仓储和服务，不放宽普通用户已有的 owner-scoped 查询。管理员查询负责：

- 总览聚合；
- 分页用户列表和用户详情；
- 跨用户任务、图片和调用查询；
- 管理员专用临时预览 URL；
- 操作记录查询。

所有列表都使用服务端分页、稳定排序和有边界的时间范围。图片字节不经列表接口返回。

### 5.3 模型调用记录

模型 Provider 继续负责外部协议，注入一个窄的调用记录端口。调用上下文由应用层明确传入：

- 图片 Worker 提供用户、任务、generation item、operation type；
- Chat 和反推提示词提供用户、会话或请求上下文。

Provider 内部只有最接近真实网络请求的位置知道一次重试是否真的发生，因此调用开始、成功、失败和 token 采集在 Provider 边界记录，不从任务数量推算。

### 5.4 审核执行

图片审核由单独应用服务处理：

- 验证状态转换；
- 验证原因；
- 在同一事务更新图片审核字段并写审计记录。

普通图片解析与 URL 签发统一检查审核状态，避免只在某一个页面隐藏但仍能通过 Chat、下载或二次编辑绕过。

## 6. HTTP 接口

接口保持资源化并复用现有 `/admin` 前缀：

- `GET /admin/overview`
- `GET /admin/users`
- `GET /admin/users/{user_id}`
- `PUT /admin/users/{user_id}/role`
- `PUT /admin/users/{user_id}/status`
- `GET /admin/jobs`
- `GET /admin/jobs/{job_id}`
- `GET /admin/images`
- `PUT /admin/images/{image_id}/moderation`
- `GET /admin/model-calls/summary`
- `GET /admin/model-calls`
- `GET /admin/audit-logs`
- 现有 `/admin/models*`

原有无分页的用户列表接口直接升级为分页契约，并同步更新管理前端；不保留双套旧接口或兼容适配层。

错误语义：

- 非管理者访问：403；
- 停用用户访问受保护接口：401；
- 资源不存在：404；
- 重复审核状态、停用自己、停用或降级最后一个有效管理员：409；
- 非法筛选、日期范围或审核原因：400；
- 调用记录无法在上游请求前创建：503，不发送上游请求。

## 7. 前端设计

新增 `AdminLayout`，包含：

- 总览；
- 用户；
- 出图管理；
- API 用量；
- 模型配置；
- 操作记录。

管理页面沿用现有设计系统，不引入第二套组件库或图表框架。第一版趋势图可使用轻量 CSS/SVG 组件；如果表格和数字已经足够表达，不为了“像后台”强行增加图表。

图片网格使用懒加载缩略图，打开详情时才请求输入图和大图预览。所有筛选条件写入 URL query，刷新和分享后台链接后仍能保留筛选状态。

普通用户页面只增加统一的不可用占位，不展示审核状态、原因或后台入口。

## 8. 失败处理与一致性

- 管理员状态修改与审计记录同事务提交；
- 非法状态转换 fail-fast，不重试、不静默吞掉；
- 数据库无法创建调用记录时不发送上游模型请求；
- 上游网络错误仍按现有 I/O 重试策略处理，每次真实重试单独记录；
- token 缺失不估算：GPT Image 2 允许为空，豆包调用标记 token 缺失并显示异常；
- 图片预览签名失败作为 I/O 错误明确返回，不用占位 URL 冒充成功；
- 历史数据不生成虚假的调用记录；报表明确标注调用明细统计起始时间；
- 屏蔽图片后不再签发普通用户 URL；此前已签 URL 接受最长约一小时的自然过期窗口。

## 9. 测试与验收

### 9.1 权限与用户

- 普通用户不能访问任何管理接口；
- 数据库角色变化立即影响现有 JWT；
- 停用用户的现有 Bearer 和 SSE token 下一次请求均为 401；
- 管理员不能停用自己；
- 最后一个有效管理员不能被停用或降级；
- 历史和新用户迁移后默认启用。

### 9.2 图片审核

- 历史和新图片默认正常；
- 正常图可屏蔽，屏蔽图可恢复；
- 重复状态转换返回 409；
- 屏蔽图在历史、Chat、下载、反推提示词、二次编辑和换背景入口均不可用；
- 管理员仍能预览屏蔽图；
- 审核修改与审计记录同时成功或同时回滚。

### 9.3 模型调用

- GPT Image 2 每次 generation/edit POST 都产生一条调用记录；
- 每次真实重试单独计数并带正确尝试序号；
- 异步 submit 计数，poll 和 CDN download 不计数；
- 成功、失败、超时和结果不确定状态正确；
- GPT Image usage 有则落库，无则保持空；
- 豆包请求带 `include_usage`，末尾 usage chunk 能落输入、输出和总 token；
- 一条 Chat 消息触发多轮模型调用时逐轮记录；
- 反推提示词调用归入豆包统计；
- 调用记录创建失败时不会请求上游。

### 9.4 管理查询与前端

- 总览聚合与明细数据一致；
- 时间、用户、模型、状态和功能筛选正确；
- 分页稳定，无重复或漏项；
- 用户、任务、图片、模型调用之间的跳转正确；
- 旧数据只展示可证明的任务、图片和成本，不显示伪造 token 或调用次数；
- 管理前端加载态、空态、错误态和无权限态完整；
- 普通用户看不到任何审核原因或管理员功能。

## 10. 明确不做

第一版不包含：

- 自动内容审核或第三方审核服务；
- 审核队列、多级审批、申诉流程；
- 图片物理删除、对象搬迁或即时撤销既有签名 URL；
- 多级管理员角色；
- 批量封禁、批量审核；
- CSV 或财务报表导出；
- 自动预算或异常用量告警；
- 图片存储生命周期清理；
- 管理员以用户身份登录；
- 历史 token 或真实调用次数推算；
- 新的成本账本或中转站账单对账系统。

## 11. 后续触发条件

以下能力只在出现明确需求时另行设计：

- 违规内容量大到人工巡检不可承受时，引入自动审核；
- 真实付费或月度 API 支出形成规模时，引入预算阈值和异常告警；
- 财务需要周期对账时，增加导出和供应商账单核对；
- 存储成本成为问题时，单独设计可恢复的归档与清理策略；
- 管理团队扩大且职责分离时，再增加审核员或只读管理员角色。
