# 并行施工任务卡（分发给各 Dev agent）

> 每个 agent 启动必读：`docs/项目状态与接口清单.md`(看板, 接口契约见 §3/§5) + `image-code/CLAUDE.md`(Dev 角色边界) + 父 `CLAUDE.md`(协作总规约)。
> 通用约束（所有卡适用）：①严格 SOLID，延续六边形(domain←ports←application←infrastructure←interface)；②Dev 不写测试(归 QA)，用 `uv run python -c` smoke 自检；③`uv run ruff check src && uv run mypy` 必须绿；④涉及 DB schema 变更**先问用户**(现有 10 表够用则不改)；⑤完成即 commit，`type: 描述`+正文，无 co-author；⑥只写 `image-code/` 与 `image-issues/`。

## 调度节奏（重要）

1. **先单独做 WP-A**（确立仓储端口形状 + 路由注册约定 + 项目编号 D3）。
2. WP-A 落地后**扇出并行**：WP-E、WP-F、WP-H（互不依赖、文件不撞）。
3. WP-B/C/D 依赖 WP-A；**WP-B 开工前先 brainstorm D2**(需求单→引擎Brief映射)。
4. WP-J(前端)完全独立，可随时按 §3 契约起骨架。WP-I/K 需用户给 key+预算。
5. **共享文件协议**：唯一高频冲突点是 `interface/api/app.py` 与 `asgi.py` 的 `include_router`。约定：WP-A 先建立"路由聚合"模式，后续每个 WP 只新增自己的 route 模块，注册行若冲突在 `image-issues` 标注错峰提交。

## WP-A · 客户 + 项目 + 4 态状态机（基座，先做，先单独）

- **依赖**：无（ORM 表已建）。**可并行**：否。
- **背景**：M2a 已建 `customer`/`project` 表与迁移，但无仓储/用例/路由。这是阶段2 基座，并为后续确立"仓储端口+用例+薄路由"范式。
- **目标**：客户/项目 CRUD + 项目 4 态状态机流转，可经 HTTP 端到端操作。
- **范围/文件**（新增为主）：
  - `ports/repositories.py`：`CustomerRepository`/`ProjectRepository` 抽象（仿 `ports/job_repository.py`）。
  - `infrastructure/db/customer_repo.py`、`project_repo.py`：SQLAlchemy 实现。
  - `application/project/project_service.py`(创建/查询/状态流转校验)、`customer_service.py`。
  - `interface/api/routes/projects.py`、`customers.py`：薄控制器。
  - `interface/api/app.py` + `asgi.py`：建立 `include_router` 聚合约定，给后续 WP 留位。
  - `domain/models.py`：按需加 `ProjectRecord`/`CustomerRecord` 读模型；状态机用现有 `enums.py::ProjectStatus`。
- **D3**：项目编号 `P{YYYYMMDD}-{NNN}`。加 `project.project_code` 列属 schema 变更，**先问用户**；未拍板前先用自增 id、code 作派生展示。
- **契约**：看板 §3.2(`/customers*`、`/projects*`、`PUT /projects/{id}/status`)；非法状态流转抛 `DomainError`→400。
- **验收**：smoke 跑通 建客户→建项目→合法/非法流转→查询；ruff+mypy 绿；commit；更新看板+进度日志。
