# Chat 中央布局与单一滚动条设计

## 目标

让 Chat 的中央对话区与页面主轴形成统一边界，将最大宽度从当前 `max-w-3xl` 放宽到 `960px`，并确保桌面端只显示一根业务滚动条。消息、出图结果和输入台必须属于同一条中央工作流，不能再呈现为彼此割裂的区域。

## 当前问题

- 中央列使用 `max-w-3xl`，桌面端实际宽度约 768px，明显窄于顶部导航和可用工作区。
- 页面 Shell、主工作区、会话列表和消息区分别承担部分高度与溢出控制，滚动职责不够直观。
- 左侧历史列表与中央消息区都使用可见的纵向滚动条，长内容场景会同时出现两根滚动条。
- 输入台虽然不在消息滚动容器内，但中央列偏窄，使参数栏、模型选择和结果卡显得拥挤。

## 选定方案

采用固定最大宽度的中央列与单一可见滚动条：

```text
AppShell（100svh，不滚动）
├─ AppTopBar
└─ Chat 主工作区（占满剩余高度，不滚动）
   ├─ SessionSidebar（可滚动，隐藏滚动条）
   └─ Chat 中央列（max-width: 960px）
      ├─ 消息区（唯一显示纵向滚动条的区域）
      └─ ChatComposer（固定在中央列底部）
```

## 布局职责

### 页面 Shell

- 继续使用视口高度 `100svh`。
- 页面根节点和主工作区保持 `overflow-hidden`，不产生浏览器页面级纵向滚动条。
- 顶部导航保持现有尺寸与位置，本次不调整导航视觉设计。

### 左侧会话历史

- 保持现有 228px 桌面宽度和独立滚动能力，避免长历史列表失去可达性。
- 隐藏滚动条轨道和滑块，但保留鼠标滚轮、触控板、触摸及键盘滚动能力。
- 不改变移动端隐藏规则和会话选择行为。

### 中央 Chat 列

- 桌面最大宽度设为 `960px`，宽度不足时使用可用空间全宽。
- 标题、消息、结果卡和输入台共用同一中央列边界。
- 保留响应式水平内边距，避免小屏内容贴边。
- 不修改消息气泡自身的最大宽度比例，防止长文本行过长；出图结果卡可随中央列获得更多空间。

### 消息区

- 作为唯一显示纵向滚动条的业务区域。
- 保持现有自动滚动到底部逻辑及 `scrollRef` 所有权。
- 消息增长、任务状态变化和图片结果回显不得推动输入台离开视口。
- 滚动条只能属于消息区，不允许父级页面再次产生纵向滚动。

### 输入台

- 保持在中央列底部并退出消息区滚动流。
- 宽度与中央列一致，最大 960px。
- 保持折叠、全屏编辑、参考图、模型和参数交互不变。
- 本次只调整布局边界，不重构输入台内部信息架构。

## 响应式行为

- `md` 以下继续隐藏左侧会话历史，中央列占满可用宽度。
- 小屏使用现有页面边距，不强制 960px 固定宽度。
- 页面仍锁定为单视口高度；虚拟键盘和动态视口变化继续由 `svh` 布局承接。
- 横向不允许出现页面滚动条；参数控件继续使用现有换行与折叠规则。

## 可访问性

- 隐藏左侧滚动条不得禁用滚动或焦点导航。
- 中央消息区应保持键盘可滚动能力。
- 不通过覆盖层或绝对定位固定输入台，避免遮挡最后一条消息和焦点元素。

## 测试与验收

1. 桌面视口下中央 Chat 列最大宽度为 960px，消息区和输入台左右边界一致。
2. 页面根节点与 Chat 主工作区不产生纵向滚动；消息区是唯一显示滚动条的业务容器。
3. 左侧会话历史在内容溢出时仍可滚动，但不显示滚动条。
4. 长对话和出图结果出现后，输入台始终保留在视口底部，消息区独立滚动。
5. 自动滚动到底部行为保持有效。
6. 移动端中央列全宽、无横向溢出，左侧历史仍按现有规则隐藏。
7. 现有 Chat 交互、状态管理和生成结果测试保持通过。

## 非目标

- 不调整顶部导航宽度或结构。
- 不重新设计输入台内部参数层级。
- 不改变消息气泡、结果卡的数据流或 SSE 行为。
- 不修改后端接口、任务状态或图片回显逻辑。
