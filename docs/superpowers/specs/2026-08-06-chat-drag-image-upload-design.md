# Chat 图片拖拽上传设计

## 目标

让用户把本地图片拖入整个 Chat 输入台并松手后立即上传。上传完成的图片继续沿用现有附件预览与消息发送链路，在发送 Chat 消息时以 `upload_ids` 提交。

本次不新增后端接口、不改变上传存储格式，也不改变 Chat 消息协议。

## 范围

- 整个展开状态的 Chat 输入台都是图片拖拽接收区。
- 支持 PNG、JPEG、WebP，与现有文件选择器及 `POST /uploads` 保持一致。
- 单轮最多保留 3 张附件；新拖入的图片与已有附件合并计算。
- 保留现有“添加参考图”和“继续添加”点击上传入口。
- 拖入新图片时取消当前生成图编辑底图，与现有点击上传行为一致。
- 上传期间禁止发送，防止消息先于图片上传完成而丢失附件。

不包含文件粘贴、全页面拖拽接收、文件夹上传、上传历史或后端批量上传接口。

## 方案选择

采用装饰器式组件 `ChatImageDropZone` 包裹 `ChatComposer` 的可视输入台。装饰器只处理浏览器拖拽事件、接收态和文件筛选，把可接受的只读 `File[]` 交给统一的 `onPickFiles` 动作；上传请求、附件状态和 Toast 仍由 `ChatPage` 负责。隐藏文件输入框同样先把 `FileList` 转成 `File[]`，点击与拖拽共用一条动作契约。

不把拖拽事件直接堆入 `ChatComposer`，避免参数控件、输入逻辑和文件协议耦合；也不在整个 Chat 页面建立全局 Drop Zone，避免用户拖过消息区时误触上传。

## 组件与职责

### `ChatImageDropZone`

- 通过嵌套进入计数处理 `dragenter` / `dragleave`，避免指针经过子元素时遮罩闪烁。
- 只在拖拽内容包含文件且接收区可用时阻止浏览器默认行为。
- 在 `drop` 时停止默认打开文件行为，筛选图片并调用 `onFiles`。
- 根据剩余附件位计算可接收数量；超出数量时只接收前 N 张，并调用明确的拒绝回调。
- 在忙碌、上传中、已满 3 张、折叠状态时不进入可接收态。
- 不发起网络请求，不保存附件业务状态。

### `ChatComposer`

- 使用装饰器包裹现有输入台主体。
- 把 `busy`、`uploadPending`、剩余数量和 `onPickFiles` 传给装饰器。
- 上传中显示缩略图占位；已有附件时继续上传也有可见反馈。
- `canSend` 增加 `!uploadPending` 条件。

### `ChatPage`

- 继续使用 `useUploadImage()` 和现有 `onPickFiles`。
- 文件按顺序上传，成功项立即追加到 `attached`。
- 单个文件失败不清除已成功附件，并显示现有上传错误 Toast。
- 对格式不支持、超过剩余数量等客户端拒绝原因显示具体 Toast。

## 交互与视觉

正常状态不增加常驻装饰。拖入图片进入输入台时，在现有 20px 圆角边界内显示一层半透明品牌浅色遮罩和品牌色虚线描边，中央使用图片上传图标和两行文案：

- 主文案：`松开即可上传图片`
- 辅文案：`支持 PNG、JPG、WebP · 还可添加 N 张`

遮罩覆盖输入内容但不改变输入台尺寸，避免布局跳动。离开接收区、松手或组件禁用时立即移除。上传开始后遮罩退出，参考图区域显示旋转进度占位；上传完成后替换为现有缩略图。

拖拽高亮只使用现有 Workbench 品牌色 Token，不引入新的视觉体系。键盘焦点、点击选图和移动端行为保持不变。

## 文件处理规则

1. `DataTransfer` 不含文件：不拦截事件，不显示接收态。
2. 文件 MIME 为 `image/png`、`image/jpeg` 或 `image/webp`：可进入上传队列。
3. 非支持格式：不上传，并提示 `仅支持 PNG、JPG、WebP 图片`。
4. 当前附件数量加新图片超过 3：只上传剩余槽位可容纳的前几张，并提示剩余图片未添加。
5. 已满 3 张：不进入接收态，松手不上传并提示先删除已有图片。
6. Chat 忙碌或已有上传进行中：不接受新的拖入文件。
7. 上传失败：保留成功附件，失败文件不生成缩略图，可再次拖入重试。

客户端筛选用于即时反馈；后端仍保留大小、格式和所有权校验，作为最终安全边界。

## 数据流

```text
本地图片
  -> ChatImageDropZone 筛选与限额
  -> ChatPage.onPickFiles
  -> POST /uploads
  -> UploadResponse { id, url }
  -> attached 缩略图
  -> sendChatMessage(upload_ids)
```

`upload_id` 仍由服务器生成。前端不从文件名推导 ID，也不在发送时重新上传。

## 错误与竞态

- 上传期间发送按钮禁用，键盘发送同样受 `canSend` 约束。
- `drop` 后立即清除拖拽态，即使上传失败也不残留遮罩。
- 使用拖拽进入计数而非单一布尔切换，避免子元素触发伪 `dragleave`。
- 组件卸载或变为禁用时清除计数和高亮。
- 不增加自动重试；网络失败继续使用现有显式错误提示和用户手动重试。

## 测试与验收

### 单元测试

- 文件拖入整个输入台时显示接收态，离开后恢复。
- Drop 图片会阻止浏览器默认行为并调用现有文件动作。
- 非文件拖拽不会被接收。
- 非支持格式被拒绝且不会上传。
- 多文件按剩余槽位截断，总附件数不超过 3。
- 忙碌、上传中和附件已满时不接收 Drop。
- 上传中发送按钮与键盘发送均不可用。
- 已有附件时上传占位可见。

### 回归验证

- 现有点击选图、继续添加、删除、反推提示词和消息发送行为保持正常。
- 前端全量测试、类型检查、Lint 和生产构建通过。
- 桌面浏览器手动验证拖入、离开、松手、连续上传和失败提示。
- 移动端保持点击选图流程，不显示不可操作的拖拽提示。

## 验收标准

用户可把 1–3 张受支持图片拖入 Chat 输入台，看到明确的接收与上传反馈；上传完成后图片出现在附件区，发送消息时对应 `upload_ids` 被提交。整个过程中不会因上传未完成而提前发送，也不会突破现有 3 张附件上限。
