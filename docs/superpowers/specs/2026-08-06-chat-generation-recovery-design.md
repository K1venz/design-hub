# 历史会话生图进度恢复设计

## 背景

“帮我设计”已经支持持久化多会话，但当前生成进度仍依赖页面内存中的 SSE 状态。用户刷新页面、切换到其他会话再返回，或网络连接中断后，正在执行的生图任务仍可由后台继续处理，前端却无法恢复任务关联、占位槽和生成动画。

根因是带 `job_id` 的 assistant 转录消息只在任务终态后写入。任务运行期间，历史转录中没有可用于查询任务详情的 `job_id`。同时，历史结果查询只执行一次，现有任务详情到槽位的转换也不支持“生成中”状态。

## 目标

- 刷新或重新进入一个仍在生图的历史会话时，立即恢复完整图片槽位和旋转动画。
- 已落库的单张结果立即显示，未完成槽位继续等待，失败槽位明确显示失败。
- 自动刷新任务详情，直至任务进入完成、部分完成或失败终态。
- 多个会话可以独立执行和恢复生图任务，任务状态不串会话。
- 当前实时生图与历史恢复使用同一套结果数据源和结果卡逻辑。

## 非目标

- 不实现 SSE 事件级断点续传或历史事件回放。
- 不持久化动画、逐字输出、步骤条或生成确认卡等页面过程状态。
- 不改变删除会话时对已提交生图任务的处理语义；删除会话不等于取消任务。
- 不在本次改动中治理后台长期停留在“生成中”的僵尸任务。
- 不增加会话列表中的跨会话实时进度徽标。

## 核心原则

SSE 是实时通知通道，不是可恢复状态的事实来源。

- `chat_message.job_id` 负责表达任务与会话的持久关联。
- `listing_job.status` 和 `listing_image` 负责表达任务当前进度与结果。
- 前端动画由持久化任务状态推导，不单独保存。

## 后端设计

### 任务关联写入时机

用户确认出图并成功创建 `listing_job` 后，后端必须在发送 `job_started` SSE 事件前，立即写入一条带 `job_id` 的 assistant 转录消息。

顺序固定为：

1. 创建生图任务并取得 `job_id`。
2. 持久化 assistant 任务消息与 `job_id` 关联。
3. 提交成功后发送 `job_started`。
4. 继续转发任务事件和助手收尾文本。

初始消息使用状态中立的文案，避免客户端断开后留下错误的“正在生成”描述。任务在线完成时，更新同一条消息的收尾文案，不追加第二条带相同 `job_id` 的消息。

`ChatSessionRepository` 的写入接口应返回新消息的稳定标识，并提供更新指定 assistant 消息内容的操作。该变更属于内部端口重构，不改变公开 HTTP API。

### 连接中断语义

任务一旦提交到后台队列，客户端 SSE 中断不得取消任务。任务继续更新 `listing_job` 和 `listing_image`。由于会话关联已在 `job_started` 前落库，用户之后可通过历史转录重新发现任务。

如果连接在任务创建成功前中断，则不存在可恢复任务，不生成虚假的历史进度卡。

### 事务与失败

会话关联写入失败时不得发送 `job_started`。错误应向上传播，不允许把一个无法恢复的任务报告为已成功启动。

任务提交和会话消息当前属于不同仓储事务。本次不引入跨聚合分布式事务；实现必须把关联写入放在公开启动事件之前，并用测试锁定顺序。若未来需要覆盖进程在两次提交之间崩溃的极端窗口，应单独设计 outbox 或统一工作单元，而不是在本次范围内加入补偿逻辑。

## 前端设计

### 单一结果渲染路径

当前实时结果和历史结果应收敛为统一流程：

```text
jobId -> 查询任务详情 -> 构建结果槽位 -> ChatResultBlock
```

当前会话从 `job_started` 获得 `jobId`，历史会话从 `chat_message.job_id` 获得 `jobId`。两者使用同一个任务结果组件。

SSE 图片事件只负责促使查询缓存尽快失效或刷新，不再作为可恢复结果槽位的唯一来源。页面内存状态不得与数据库任务详情长期维护两套互相竞争的结果事实。

### 生成中槽位恢复

任务详情到结果槽位的转换必须支持 `status='生成中'`：

- 总槽位数来自任务的 `n`。
- 已落库成功图片填入真实图片槽。
- 已明确失败的单图填入失败槽。
- 剩余数量补齐为空槽，并由 `ChatResultBlock` 显示旋转动画。
- 已处理数包含成功和明确失败的槽位，防止单张失败后进度永久少一。

任务仍在生成且尚无图片时，也要返回 `n` 个空槽，不能返回空数组或隐藏结果卡。

### 自动刷新

任务状态为“生成中”时，任务详情查询使用固定间隔自动刷新。进入以下任一终态后停止：

- 完成；
- 部分完成；
- 失败。

切换到其他会话后，已卸载结果组件不再主动轮询。重新进入时立即查询最新状态。只有当前打开会话内仍在运行的任务会持续刷新。

### 展示规则

- 生成中：展示 `已处理数/总数`、标题旋转图标和未完成槽位动画。
- 部分完成：保留成功图片，失败槽明确显示，停止动画。
- 完成：展示全部可用图片，停止动画。
- 失败：展示失败终态，停止动画。
- 任务详情无法获取：明确显示“出图结果已失效或无法载入”，不伪装成生成中。

## 多会话行为

每个会话只通过自身转录中的 `job_id` 恢复任务。选择会话 A 时不会查询会话 B 的运行任务，因此状态不会串会话，也不会因历史会话数量增加而全局轮询。

关闭会话 A 的 SSE 只是停止观看实时流。已经提交到任务队列的 job A 独立继续运行。回到会话 A 后，前端从转录恢复 `job_id`，再从任务详情恢复进度。

一个会话内存在多个带 `job_id` 的消息时，每个任务独立渲染；只有仍处于“生成中”的任务轮询。现有会话任务数量上限继续生效。

## 现有功能冲突检查

### 实时聊天与 SSE

- 保留现有 session、assistant_delta、step、tool_call、generation_confirm、job_started、job_event 和 assistant_end 事件契约。
- `job_started` 的可见时机只增加“会话任务关联已经持久化”的前置保证。
- 助手流式文本和确认流程不改为轮询，只有出图结果统一由任务详情驱动。

### 生成确认令牌

- `confirm_token` 仍为内存中的短期一次性过程态，不写数据库。
- 只有确认成功并实际创建 job 后才写持久化任务消息。
- 取消确认不会产生 job 关联或结果卡。

### 工作台和出图历史

- `listing_job`、`listing_image` 和公开任务详情结构保持不变。
- 任务详情查询的“生成中自动刷新”应由调用方或明确的查询策略控制，避免无条件改变所有历史页的网络行为。
- 槽位构建逻辑扩展为支持生成中任务，不能破坏完成、部分完成和失败的现有映射。

### 会话历史与删除

- 继续使用现有 `chat_message.job_id`，不新增或修改数据库列。
- 会话删除仍级联删除转录消息，但不取消或删除已经提交的 `listing_job`。
- 历史消息仍按 `seq` 排序；更新任务消息内容不得改变消息顺序。

### 图片操作

- 图片预览、下载、继续编辑、换背景和反推提示词继续依赖终态图片的 `image_key` 和现签 URL。
- 未完成占位槽不暴露这些操作。

### React Query 缓存

- 查询键继续使用现有 `['listing', 'job', jobId]`，实时和历史视图共享同一缓存。
- SSE 收到任务事件时可刷新同一查询键，不创建第二套任务缓存。
- 轮询在终态或组件卸载时停止。

## 测试设计

### 后端

- 任务创建后、任务终态前，获取会话转录已经包含对应 `job_id`。
- `job_started` 只有在任务消息持久化成功后才发出。
- 正常完成时更新同一条任务消息，不产生重复 `job_id` 消息。
- 取消确认不写任务消息。
- 两个会话各自提交任务时，转录中的 `job_id` 不交叉。

### 前端纯逻辑

- 生成中且零结果时，根据 `n` 返回全部空槽。
- 生成中且部分结果已落库时，正确组合真实图片、失败槽和等待槽。
- 已处理数量同时计算成功和明确失败。
- 完成、部分完成和失败的原有槽位映射保持不变。

### 前端组件与查询

- 历史消息带 `job_id` 时渲染任务结果卡。
- 生成中任务显示完整占位槽和旋转动画。
- 查询在生成中持续刷新，在终态停止。
- 切换离开会话后停止该视图的主动刷新，重新进入后恢复查询。
- 当前任务和历史任务使用同一结果组件，不重复渲染同一个 job。

## 验收标准

1. 会话 A 生图期间切到会话 B，再切回 A，能够看到最新已完成图片和剩余槽位动画。
2. 会话 A 生图期间刷新浏览器，恢复后的表现与切回会话相同。
3. 恢复后图片逐张更新，任务终态后动画和轮询自动停止。
4. 两个会话同时生图时，各自只显示自己的任务和进度。
5. 单张失败、部分完成和整单失败均能进入明确终态，不无限旋转。
6. 当前实时聊天、生成确认、会话历史、会话删除、工作台历史以及图片后续操作无回归。
