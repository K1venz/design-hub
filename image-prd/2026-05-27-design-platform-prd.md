## 1. 背景与目标

### 1.1 业务痛点

| 序号 | 痛点 | 当前数据 |
|---|---|---|
| P1 | 第三方生图工具单价高（GPT-image / nano-banana 类） | 4 元/张，损耗 30%，**实际成本 6 元/张** |
| P2 | 免费工具（豆包等）质量差，需人工二次编辑 | 设计师返工率高，人力成本失控 |
| P3 | 客户需求对接靠聊天记录，无结构化沉淀 | 需求漏接、改稿漏改频发 |
| P4 | 项目素材散落本地，无统一管理 | 复用率低，跨项目调取困难 |
| P5 | 多模型生态分散（GPT-image、千问、Seedream、万相、灵动），缺统一调度 | 无法按场景调度最优模型 |

### 1.2 产品定位

> **"设计师的 AI 副驾驶中台" —— 以「产品图 → 高质量电商图」为核心引擎，串联需求对接、多模型调度、改稿管理的工作流编排平台。**

**不做什么**：
- ❌ 不抢稿定 / Canva 的模板生意
- ❌ 不和 GPT-image / Seedream 拼底层模型能力
- ❌ V1 不对外售卖（不做 SaaS，不做私有化分发）

**做什么（V1 三层定位）**：
- 工作流编排层（一单一档的项目管理）
- 多模型智能路由层（5 个模型 × 3 个档位的成本/质量调度）
- 设计师效率工具层（需求单、改稿单、批量导出）

### 1.3 V1 目标与验收标准

| 维度 | V1 目标 | 验收方式 |
|---|---|---|
| **单张成本** | ≤ 0.3 元（目标 ~0.14） | 跑满 200 张真实订单后加权均价 |
| **首次可用率** | **全场景 ≥ 70%**（两阶段合成实际 75-80%） | 设计师评分 ≥ 4 星 占比（转人工任务不计入分母） |
| **产品一致性** | 走两阶段合成 ≥ 95%（原像素保真） | 人工肉眼审核 |
| **人力节省** | ≥ 30% | 对比项目启动前的人工流程耗时 |
| **完整业务闭环** | 接单 → 出图 → 改稿 → 交付 全流程可走通 | 至少 5 个真实项目跑通 |
| **客户档案沉淀** | ≥ 5 个客户，复用录入时间 ≥ 50% | - |

### 1.4 V1 非目标（明确不做）

- 不做聊天记录 → 需求单的全自动解析（V2）
- 不做 AI 素材自动分类（V2）
- 不做竞品风格爬取与归纳（V2）
- 不做 AI 模特试衣（S2 场景）
- 不做海报合成 / 版式系统（S5 场景，V2）
- 不做工作流可视化编辑（V2+）
- 不做 AI 自动评分（V2）
- 不做模型自研/自训、ControlNet 自部署（注：S1/S3 的抠图+合成用现成开源模型 BiRefNet + 程序合成，属工程手段，不是自研模型）
- 不做多租户、私有化部署给同行
- 不做业务/接单人员角色（仅设计师 + 管理者）

## 2. 业务模式与用户角色

### 2.1 业务模式

- 服务对象：**外部品牌客户订单（主） + 内部业务方需求（次）**
- 产能预期：1000-2000 张/月
- 行业范围：电商素材设计，**全品类**（不押 3C / 服饰 / 美妆等单一垂类）
- 部署形态：内部中台，单租户，自家服务器 / 阿里云

### 2.2 用户角色

| 角色 | 占比 | 核心动作 | 权限来源 |
|---|---|---|---|
| **设计师** | 70% | 上传产品图 → 录需求单 → 出图 → 选稿 → 改稿 → 交付 | 自助注册默认角色 |
| **管理者** | 30% | 查看仪表盘、成本统计、解锁预算、维护模型配置 | 管理者在用户管理后台提升（首个由启动 seed 创建） |

V1 **不引入**业务/接单人员角色，设计师自行录入客户需求。

### 2.3 单据形态：项目（一单一档）❌ 已废止（2026-06-12 世界 A 移除，见 §0 定性修订）

每个客户订单 = 一个项目。项目是中台所有数据组织的根。

项目状态机：

```
[需求录入] → [设计中] ⇌ [客户审稿] → [已交付]
                ↑              │
                └──────────────┘
                  (改稿循环，带轮次号)
```

| 状态 | 说明 |
|---|---|
| 需求录入 | 设计师正在填写需求单 |
| 设计中 | 出图、选稿、改稿（轮次递增） |
| 客户审稿 | 已发给客户，等待反馈 |
| 已交付 | 终态，归档 |

### 3.2 V1 支持的 3 个子场景 + 生成策略

> ⚠️ 下表「生成方式 = 两阶段合成」为初版设计，已被 gpt-image-2-vip 直出取代（见 §3 现状变更 / §3.12）。S1/S3/S4 现统一走直出，不再抠图分阶段；首次可用率口径随之改为 §3.12.6 的 50–60%（非两阶段的 ≥70%）。

| ID | 子场景 | 输入 | 输出 | 生成方式 | V1 |
|---|---|---|---|---|---|
| **S1** | 商品主图换背景 | 产品白底图 | 产品在新场景里 | **两阶段合成** | ✅ |
| **S2** | AI 模特试衣 | — | — | — | ❌ 不做 |
| **S3** | 商品场景图 | 产品图 + 使用场景描述 | 使用场景图 | **两阶段合成** | ✅ |
| **S4** | 多角度/姿势裂变 | 多角度实拍图（优先）/ 单角度图 | 同款多角度 | **多角度→两阶段合成；单角度→AI 兜底/转人工** | ✅ |
| **S5** | 海报合成 | — | — | — | ❌ 押 V2 |

#### 3.2.1 两阶段合成 vs 纯 AI（命中率决策）

裸 AI 图生图对带 Logo/复杂材质的产品图，真实首次可用率仅 **40-55%**（材质错误率 62%、Logo 漂移），达不到 70% 目标。**全场景硬指标 ≥70%**，解法是尽量让所有场景都走两阶段合成保真：

| 维度 | 两阶段合成 | 纯 AI 图生图（仅单角度 S4 兜底） |
|---|---|---|
| 产品一致性 | **100%（原像素，BiRefNet 抠图）** | 概率事件（AI 重画） |
| 流程 | 抠图 → AI 造景 → 合成 → 光影协调 | 模型直接生成 |
| 首次可用率预期 | **75-80%** | 50-60%（不达标转人工） |
| 单张成本 | **0.10-0.15 元** | 0.3-0.4 元 |

**S4 多角度的双路径（关键：保证 S4 也 ≥70%）**：

| 路径 | 触发条件 | 做法 | 命中率 |
|---|---|---|---|
| **路径 A（主，覆盖多数）** | 客户提供多角度实拍图 | 对每个角度走两阶段合成换背景 | **75-80%** ✅ |
| **路径 B（兜底，少数）** | 仅有单角度图 | 多视角模型（即梦/可灵/Zero123++）+ 9-12 候选 + 人工筛；全部 <4 星 → **转人工** | 目标 70%，不达标转人工 |

> 客户产品图一般多角度齐全（电商详情页刚需），路径 A 覆盖绝大多数 S4，故 S4 整体稳过 70%。单角度的少数情况由路径 B 兜底，转人工的任务不计入 AI 命中率分母。

**关键设计**：把"产品一致性"从不可控的 AI 生成环节，转移到确定性的程序合成环节（产品像素直接来自原图）。三场景（S1/S3/S4）均以两阶段合成为主路径。

**抠图模型**：BiRefNet（本地部署，~0 成本，毫秒级，发丝/透明边缘专门优化）。**不用 GPT-image 去背景**——生成式模型会重画产品像素导致失真，违背保真初衷。

### 3.4 Prompt 编排子系统（质量命脉）

> 完整编写规则、骨架公式、词库见配套文件 [`prompt-engineering-playbook.md`](./prompt-engineering-playbook.md)（基于 38 份真实电商 Prompt 样本归纳）。本节是 PRD 层面的需求定义，playbook 是实现依据。

#### 3.4.1 编排器数据流

```
需求单 8 字段 + 参考图 + 子场景(S1/S3/S4)
        ↓
① 视觉理解辅助（识别产品类型/主色/材质/形状/Logo 位置）
        ↓
② 选模板族（按物料类型 + 风格调性 → 9 族之一）
        ↓
③ 按族骨架填槽（变量槽 + 固定结构）
        ↓
④ 注入歧义防御词（按品类）+ 中文场景化负面句（按场景）
        ↓
⑤ 追加质量词 + 比例参数（按目标模型）
        ↓
⑥ 模型差异化后处理（Provider.postprocess）
        ↓
最终 Prompt（按模型语言/格式适配） + Negative Prompt
```

#### 3.4.2 模板族 ≠ 子场景（两个正交维度）

| 维度 | 含义 | 取值 |
|---|---|---|
| **子场景**（S1/S3/S4） | 图生图任务类型 | 换背景 / 场景图 / 多角度 |
| **模板族** | 成品的 Prompt 结构骨架 | 9 族（见下表） |

一个 S1 换背景任务，既可用「族 4 高端商业摄影」也可用「族 1 大透视海报」结构 —— 由设计师按需求选定。

#### 3.4.3 9 大模板族（每族结构独立，骨架公式见 playbook）

| 族 | 名称 | 适用 | V1 范围 |
|---|---|---|---|
| 族 1 | 大透视广告海报 | 时尚/快消/配件（产品+模特） | 🟡 V1.x（含真人，先观望） |
| 族 2 | 结构光效/X射线 | 高端 3C 内部展示 | 🟢 V2 |
| 族 3 | 极简电商主图 | 美妆/护肤/保健 | 🔴 **V1 必做** |
| 族 4 | 高端商业摄影 | 单品精修/首图 | 🔴 **V1 必做** |
| 族 5 | 氛围沉浸场景 | 食品/咖啡/生活方式 | 🔴 **V1 必做** |
| 族 6 | 双语规范+排版 | 系列化项目（统一 VI） | 🟢 V2 |
| 族 7 | 中式节庆促销 | 年货节/国潮/IP 大促 | 🔴 **V1 必做** |
| 族 8 | 字效/标题字 | 电商标题字 | 🟢 V2 |
| 族 9 | 创意超现实 | 概念海报/微缩世界 | 🟡 V1.x |

**V1 内置 4 族**（族 3/4/5/7），覆盖电商主图、详情、海报、节庆的绝大多数；含真人的族 1/9 押 V1.x，3C 结构/字效/双语押 V2。

#### 3.4.4 10 条通用编写法则（强制注入）

编排器对每个 Prompt 强制套用 playbook §二 的 10 条法则，核心 5 条：

1. **场景/风格定调放第 1 句**（模型前置词权重最高）
2. **色卡级色彩描述**（用 HEX/具名色，不用"暖色调"泛词）
3. **预判歧义主动约束**（按品类注入防御词，见词库 C）
4. **反向约束用中文场景化否定**（不用 SD tag，见词库 B）
5. **文字/版式信息独立成段**（内容+位置+字号+字重+字体名+颜色）

#### 3.4.5 5 个可复用词库（管理后台可维护）

| 词库 | 内容 | 用途 |
|---|---|---|
| A 风格→色卡 | 7 种风格 × 色卡 HEX | 填充色彩槽 |
| B 中文负面句库 | 按场景的否定句 | 生成 negative |
| C 歧义防御库 | 按品类的防御词 | 防变形/遮挡/肖像权 |
| D 质量增强词库 | 按模型的质量词 | 收尾质量词 |
| E 镜头库 | 按用途的摄影术语 | 摄影类构图 |

### 3.5 多模型路由表（模板族 × 档位 二维，管理后台可热更新）

路由从「场景×档位」升级为「**模板族×档位**」——因为不同模板族对模型能力的要求不同（含真人+复杂版式的族必须 GPT-image，极简风国产模型更划算）。

**主维度：模板族 → 首选模型**

| 模板族 | 首选模型 | 理由 |
|---|---|---|
| 族 3 极简电商主图 | **Seedream 5.0** | 极简风国产强，成本低 |

| 场景 \ 档位 | 草稿档 | 标准档（默认） | 精修档 |

### 3.9 cost-guard 成本守门中间件

`@cost_guard` 装饰器在生成任务入队前执行：

1. 预估本次成本 = 候选数 × 模型单价
2. 查询当前用户本月已用 + 公司本月已用
3. 校验 3 条红线：
   - 单次任务 > 公司剩余预算 50% → 拒绝
   - 用户本月已用 ≥ 月度配额 → 拒绝
   - 公司本月已用 ≥ 总预算 → 拒绝（需管理者手动解锁）
4. 通过 → 预扣额度；任务失败 → 回滚额度

| 控制项 | 默认值 | 谁可改 |
|---|---|---|
| 单次任务最多候选数 | 12 张（硬上限） | 管理者 |
| 单个设计师月度预算 | 200 元 | 管理者 |
| 全公司月度预算 | 800 元 | 管理者 |
| 月度预算 80% 时告警 | 钉钉/邮件通知 | 系统 |
| 月度预算 100% 时 | 停止生成，需管理者手动解锁 | 系统 |

### 3.12 电商 listing 一键出图（轻量链路）

> 来源：用户 2026-06-04 拍板新增；后端 spec `docs/superpowers/specs/2026-06-04-listing-image-generation-design.md`。
> 落地 ISSUE-0021；依赖 ISSUE-0025（上游字段对齐）、ISSUE-0020（前端）、ISSUE-0022（下拉话术）。

#### 3.12.1 形态与定位
比「项目 → 需求单 → 选模板族 → 重编排」更轻的**一键直出**形态。MVP 用同一份合成 prompt 出 N 张候选，**不做镜头分型**。

**输入**：
- 同一产品原图 **≤3 张**：先经 `POST /uploads` 独立上传（拿 `{id,url}`、前端预览），出图时带 **`upload_ids` 引用**（2026-06-04 用户改：**先上传预览 → 再出图**，取代原 multipart 直传；接口见 §3.12.8）
- 下拉：电商平台 / 国家地区 / 语言 / 比例
- 自由文本「商品卖点 & 要求」= 用户 prompt（**直出的唯一质量杠杆**）
- 张数下拉

**链路**：`POST /uploads`（上传 ≤3 图、预览）→ `POST /listing/generate`（带 `upload_ids`）→ 服务端按 id 读回图 + 拼 prompt → gpt-image-2-vip `/images/edits` → 异步队列 + SSE 出 N 张。**复用**基础设施（CostGuard / SSE / 落库口子），**不复用**两阶段合成与编排器（直出链路无需路由，live edit 模型仅 gpt-image-2 一个）。

#### 3.12.2 下拉枚举（首版）
| 下拉 | 取值 |
|---|---|
| 电商平台（4，2026-06-09 收窄国内） | 淘宝天猫1688、拼多多、京东、抖音电商（去跨境 亚马逊/Temu/TikTok Shop → 非法 400，见 §3.12.11） |
| 国家地区（1，2026-06-09 收窄固定中国） | 中国（前端去下拉但**固定发 region=中国**；后端只收窄 `_SEED_FRAGMENTS` 枚举、不做默认注入；其余 美国/欧洲/俄罗斯/东南亚 → 非法 400，见 §3.12.12） |
| 语言（2，2026-06-09 收窄） | 中文（默认）、英文（去 俄语/西语 → 非法 400） |
| 比例（4，不变） | 1:1、3:4、9:16、16:9 |
| 张数（固定 1，2026-06-09） | 前端表单固定发 n=1、去张数下拉（后端保留 1..7 校验不动、不破坏契约） |

> 下拉以通用 `modifiers` key→value 传输，增删下拉值只改后端话术片段表（image-prompt / ISSUE-0022），API 契约不变。各下拉值的正式中文话术由 image-prompt 产出。

#### 3.12.3 比例 → 尺寸映射
**以 QA 真实 e2e 实测为准**（ISSUE-0023 用例14，2026-06-04 真花钱）：上游 image2-vip 文档称"仅支持 2048 系列"，但实测 **`1024x1536`（3:4）真实出图成功、质量正常、¥1.19/张**。故 MVP 采用**已验证的 1024 系列**：

| 比例下拉 | 实际出图尺寸 | 状态 |
|---|---|---|
| 1:1 | 1024×1024 | 同系列（1024×1536 已实测，本尺寸待覆盖） |
| 3:4 | 1024×1536 | ✅ **已实测出图成功** |
| 9:16 | 1024×1536 | 竖版（同 3:4 尺寸；非精确 9:16） |
| 16:9 | 1536×1024 | 横版（同系列，待覆盖） |

> 文档与实测不符（文档 2048 系列 vs 实测 1024 可用），**以实测为准**，详见 ISSUE-0025。非表内比例 → 400 fail-fast。
> 「2048 高清档」如电商需更高分辨率可作后续增强（需另跑受控实测确认上游支持 + 成本）。

#### 3.12.4 张数与上游 n=1 限制
上游 image2-vip **`n` 仅支持 1**（一次返回 1 张，2026-06-04 用户确认接受）。故：
- 前端张数下拉（1/3/5/7）= 用户要的**候选数**；
- 后端对上游**每次恒发 `n=1`**，选 N 张 → 后端**并发/串行 N 次单图请求**，聚合返回 N 张候选（每张独立 seed/计费）；对用户仍是「一键 N 张」。
- 实现见 ISSUE-0025（上游字段对齐 + N 次单图改造）。

#### 3.12.5 成本
单次 = N 张 × gpt-image-2-vip 单价。复用 cost-guard 预扣 → 按实回正 + 月预算 80% 告警。**MVP 不另设单用户日上限**（沿用现有预算守门）；vip 实扣单价待开发核（ISSUE-0025）。

#### 3.12.6 验收标准（QA 据此出用例）
| 维度 | 口径 |
|---|---|
| **首次可用率** | **50–60%**（纯 AI 直出务实口径；**不套用两阶段合成的 ≥70%**——后者靠抠图保真，直出无此保真，§3.2.1 自述纯 AI 仅 40–55%，提示词优化目标 50–60%） |
| 时延 | 单次 N 张并发，受上游 edit ~187s/张 制约；P95 ≤ 5 分钟（N ≤ 7） |
| 成本 | 单张 ≤ 上游 medium 档单价；单次预扣不超月预算守门线 |
| 错误处理 | 图数 > 3 / 张数档非法 / 比例不在表 / modifiers 不可解析 / 未知下拉值 → 4xx fail-fast，不静默降级 |
| 出图正确性 | ≤3 张参考图真实送达上游 `image` 字段；prompt 含卖点文本 + 下拉话术片段 |

#### 3.12.7 镜头分型（押后第二迭代）
主图白底 / 特写细节 / 使用场景 / 卖点信息图 / 尺寸说明 / 生活方式 / 对比图——**MVP 不做**，列入**第二迭代**（listing 套图核心价值，待 MVP 直出链路验证后排期）。其他押后：从资产库选图、category/style 智能匹配、「AI 帮写」。（出图历史持久化已升级为生产级，见 §3.12.9。）

#### 3.12.8 图片上传接口（先上传预览 → 再出图）
2026-06-04 用户拍板 listing 改**两步**——先独立上传、预览，再出图引用，**取代** spec 决策 0a 的「multipart 直传」。

- `POST /uploads`（鉴权 Bearer）：`UploadFile` → 存储 → `{id, url}`。
  - fail-fast 校验：大小 ≤ 10MB、格式白名单（png/jpg/webp）、违例 → 4xx。
- `GET /uploads/{id}`：后端读图代理，返回图片 bytes 供前端预览（不暴露 `file://`）。
- `POST /listing/generate` 改带 `upload_ids`（≤3），后端按 id 从存储读回 bytes 发上游 edit。
- **存储 = 服务器本地磁盘**（已规划，挂进 docker api 容器持久化卷）：
  | 用途 | 路径 |
  |---|---|
  | 上传产品图/参考图 | `/data/docker/design-hub/assets/` |
  | AI 出图落点 | `/data/docker/design-hub/generated/` |
  | 导出归档 | `/data/docker/design-hub/exports/` |
  - 沿用 `LocalAssetStore`（base_dir 指向 `assets/`），**不引入 OSS**；预览经 `GET /uploads/{id}` 代理。OSS 公网/CDN 作后续增强（需凭据）。

> 落地见 ISSUE-0026（开发）；前端两步流改造见 ISSUE-0020；QA 用例14 改版。

#### 3.12.9 任务持久化与历史（生产级）
2026-06-05 用户拍板：listing 每次出图**持久化**（任务 + 每张生成记录 + 输入图）+ **历史查看**。生产级、非 MVP。
**硬约束：全独立新增、零改动现有接口**（不碰 `generation_job`/`image_store`/海报流/项目流）。表方案 **B（新建 listing 专表）**。

**新建 3 表**：
- `listing_job`：id / user_id / prompt / modifiers(JSON) / platform(冗余,筛选) / ratio / size / n / status(生成中·完成·部分完成·失败) / total_cost / error / created_at / completed_at
- `listing_image`：id / job_id / **image_key（文件名,不存绝对 url）** / seed / cost / status / created_at
- `listing_job_input`：job_id / upload_key / ord（输入产品图回显）

**持久化**：`ListingHistory` 端口的 DB 实现替 `NoOpListingHistory`（仅改 listing 装配）；出图结束写任务+图+输入。部分失败 → 任务 `部分完成`，成功图照存。

**历史端点**（listing 独立，user_id 隔离，只看自己的）：

#### 3.14.1 「帮我设计」对话历史持久化 + 回显（需求 · 2026-07-02，ISSUE-0051）✅ 已上线 prod（2026-07-06，待用户复核关账）

**① 核心设计取舍（用户已认）**：
- **存「对话转录（transcript）」、不存「事件回放」**：流式吐字/步骤条/费用确认卡等**过程态不落库**；只存最终转录（user 消息 + assistant 最终答复 + 该轮触发的 `job_id`）。

**② schema（✅ 用户亲签 2026-07-02，两表新增、不动任何现有表）**：

#### 3.17 登录健壮性四件套（需求 · 2026-07-08，ISSUE-0058）✅ 已上线 prod（2026-07-08 半天闭环，零建表零签字）
> **背景**：用户 2026-07-08「先优化登录的健壮性」+ 追加拍板「密码传输公钥加密」。spec 定稿 `docs/superpowers/specs/2026-07-08-login-robustness-design.md`（coordinator 派单 `e75ddb1`）。与 key 事故无依赖、纯登录链路、插空档做。**零建表零签字**（RSA 私钥走 .env/文件不入库）→ 无 DB 铁律门。

**① 现状缺口（读码实锤）**：a. **24h 必踢**（JWT HS256 固定 `jwt_ttl_hours=24`、无续期，活跃用户每天中途被踢、「记住我」语义半空）；b. **多标签页不同步**（登出仅清本页、无 storage 广播，别页续旧会话至撞 401）；c. **限流/网络错非人话**（nginx 429 非 JSON body、断网 fetch 异常→前端显原始错）；d. **密码明文进请求体仅靠 TLS**（prod 自签证书、用户点警告访问=TLS 实际削弱）。

**② 四件套**：
- **①滑动续期（方案 A，dev）**：活跃即永续、不活跃 24h 过期（安全兜底不变）。`CurrentUserDep` 解析 JWT 后判令牌年龄——**签发超 `jwt_renew_after_hours`（settings 默认 12）** 则签新 24h 令牌放响应头 `X-Renewed-Token`；**零端点零表零迁移**、幂等、exp 过期仍 401 走原路（SSE 长连不续、下个普通请求会续）。前端 client 响应中间件读头→`setToken`（经 rememberAwareStorage 落原存储位、不升降级）。
- **②密码传输公钥加密（dev+frontend-b）**：服务器生成 **RSA-2048** 密钥对（私钥 `.env`/文件 chmod600、**不入库不入 git**、qa/prod 各自生成）；`GET /auth/pubkey`（公开可缓存）返 SPKI PEM；login/register 密码字段改收 `base64(RSA-OAEP-SHA256 密文)`→解密→**bcrypt 照旧**；解密失败→400 人话。前端 WebCrypto importKey+encrypt，**公钥拉取失败=报错不回退明文（假加密纪律·fail-fast）**。⚠️ **bcrypt/最短 8 位校验语义不动**（min_length 校验挪到解密后明文上）。
- **③多标签页登出同步（frontend-b）**：`storage` 事件监听 auth 键被清→本页 clear+跳登录（仅登出方向广播；sessionStorage 无跨页事件→仅 localStorage 模式生效=记住我默认勾覆盖主流）。
- **④登录/注册错误人话化（frontend-b）**：429→「尝试太频繁，请稍等 1 分钟再试」；网络异常→「网络异常，请检查连接后重试」；401 维持「邮箱或密码错误」；409/400 维持现文案。

**③ 安全边界（诚实入档）**：密码加密层挡**被动嗅探/日志泄漏/自签场景偷看**；**不挡全能主动 MITM**（能改 JS）——**根治 = 备案后正式域名 + LE 证书**（联动 §7.A，本层是纵深防御永久保留）。不做前端哈希（pass-the-hash 假安全）、不做 SRP（YAGNI）。**不做服务端撤销**（无表 YAGNI，随二期方案 B 双令牌再议·记 backlog）。

**④ 部署纪律**：前后端**必须同波原子上**（密码字段格式变了）；旧缓存 bundle 发明文→400 清晰报错、刷新即愈（内测规模可接受）。零迁移轮（用户预授权绿即上）。

**⑤ 验收标准（QA，spec §五 6 条）**：0. 抓包 login/register 请求体**无明文密码**（密文 base64）+ 错密文 400 + 公钥接口挂→前端报错不发明文 + bcrypt 存储不变老账号照常登录；1. 半衰期前无续期头/令牌不变，半衰期后带新令牌无感换、存储位不变（记住我勾/不勾各验）；2. 过期令牌仍 401+清会话跳登录；3. 双标签页（localStorage）A 登出→B 秒内清跳登录；4. 429/断网显人话；5. 全站零回归（登录/注册/受保护页/chat/工作台）。

**⑥ 范围外（YAGNI，backlog）**：方案 B 双令牌（30 天离线+服务端撤销+建表签字）/ 账号锁定·验证码（nginx 限流已挡暴力破解）/ 邮箱验证 / 登录设备管理。

**⑦ 分工**：PM 本节（PRD+ISSUE-0058 挂账）→ **dev**（后端滑动续期 + 密码解密，jwt_service issue-age + CurrentUserDep 注入头 + `/auth/pubkey` + pytest）+ **frontend-b**（client 读头换令牌 + WebCrypto 加密 + storage 登出广播 + 错误人话 + vitest）**同波原子** → **QA**（验收 6 条，本机 mock 全验零成本、短 TTL 加速续期验证）→ 零迁移轮部署（coordinator 编排）。**仍内测灰度**（7.B/7.A 前置不变）。

### 6.3 关键设计细节

#### 6.3.1 SSE 实时进度（A5）

```
arq Worker  ─publish─→  Redis Pub/Sub Channel `task_events`
                                  ↓
                          FastAPI SSE Endpoint
                                  ↓
                          EventSource (前端)
```

- 任务关键事件：`task_started` / `model_called` / `image_generated` / `task_completed` / `task_failed`
- 前端按事件流更新进度条 + 增量显示已生成的候选图
- nginx 需开启 `proxy_buffering off` 防止 SSE 缓冲

#### 6.3.2 AbstractModelProvider 适配层（B4）

```python
class AbstractModelProvider(ABC):
    name: str
    unit_cost: Decimal  # CNY per image

    @abstractmethod
    async def generate(
        self,
        prompt: str,
        negative_prompt: str,
        reference_images: list[bytes],
        size: tuple[int, int],
        n: int,
        seed: int | None = None,
    ) -> list[GeneratedImage]:
        ...
```

- OpenAI / Dashscope / Volcengine 各自实现 Provider 类
- 同步 SDK（如部分国产 SDK）用 `asyncio.to_thread` 包装
- 统一返回 `GeneratedImage(url, seed, latency, cost)` 结构

#### 6.3.3 认证授权（B6）

**自建「邮箱 + 密码」认证**（替换原飞书/钉钉 OAuth）。JWT 会话层（HS256）沿用，仅替换"如何获得用户身份"。

```
注册：邮箱 + 密码 + 姓名
            ↓
       后端校验（邮箱唯一、密码 ≥8 位）→ bcrypt 存密码哈希
            ↓
       建号（默认角色 = 设计师）→ 签发 JWT（HS256，TTL 过期）
            ↓
登录：邮箱 + 密码 → bcrypt 校验 → 签发 JWT
            ↓
       前端存 LocalStorage，请求带 Authorization: Bearer <JWT>
```

**角色来源**（不再依赖部门映射）：
- 注册默认 **设计师**：任何人邮箱 + 密码自助注册即用。
- **管理者** 由管理者在「用户管理后台」提升/降级；保护"最后一个管理者不可降级"。
- 首个管理者：启动 **seed**（邮箱/密码从 `.env` 读，不入库、不写死；建议首登后改密）。
- 角色变更于该用户**下次登录**生效（已签发 JWT 在 TTL 内角色不变，可接受）。

**本期不做（YAGNI）**：邮箱验证、忘记密码/邮件重置、第三方 OAuth。`app_user.email` 为以后找回/通知留口。

- **法定要求**：《生成式 AI 服务管理暂行办法》+《人工智能生成合成内容标识办法》（2025-09 已施行）→ ① 上传图 + 生成图**内容审核**（可接火山引擎内容安全 API，与 TOS 同云厂商）；② AI 生成内容**标识义务**；③ 算法/服务备案义务（我们是 API 调用方非自训模型，边界需**法务确认**）。
- **标识方案细化（与「prompt 禁水印」的合规适配，PM）**：两者**不冲突、层次不同**——prompt 禁的是出图模型**臆造**假水印/假 logo（生成时、画面内），合规标识是**生成后**附加：
  1. **隐式标识（首发必做）**：生成图文件元数据（EXIF/XMP）嵌入 AI 生成标识 + 服务提供者信息——出图后处理管道加一步，零画面影响；
  2. **页面显式声明（首发必做）**：产品界面/结果页/下载处显著标注「内容由 AI 生成」+ 用户协议 AI 条款（与 7.E 联动）；
  3. **画面内可见标识的边界 = 法务确认项**：电商商品图烧可见角标伤商用价值，「何种场景必须画面内显式标识」留法务咨询后定，**不自行拍**。
