# Kimi K3 替换豆包 Chat 与现阶段容量成本方案

> 调研日期：2026-07-24  
> 文档性质：只读审计后的产品与技术决策记录  
> 决策范围：Kimi K3 只替换 Chat / Planner 角色；图片生成继续使用 APINebula `gpt-image-2`  
> 证据规则：`[CODE]` 当前代码、`[RUNTIME]` 只读运行验证、`[TEST]` 自动化测试、`[DATA]` 当前本地数据、`[OFFICIAL]` 官方资料、`[INFERENCE]` 基于证据的测算、`[UNKNOWN]` 尚缺证据

## 1. 结论摘要

现阶段不应把 Kimi K3 当成图片生成模型，也不应期望接入 Kimi K3 后降低单张图片成本。

正确的职责拆分是：

```text
用户自然语言和产品图片
→ Chat / Planner：豆包 2.0 或 Kimi K3
→ 需求理解、结构化、工具选择、Prompt 规划
→ Renderer：APINebula gpt-image-2
→ 图片生成、编辑和最终图片输出
```

推荐决策：

1. 图片生成链保持 `gpt-image-2`，不因接入 Kimi K3 而变更。
2. Kimi K3 的候选位置是替换豆包承担 Chat / Planner 职责。
3. 当前最值得利用的 K3 能力是视觉理解、严格 JSON Schema、工具调用和复杂需求规划。
4. K3 不会直接提高渲染模型画质，但有机会通过更准确的需求理解和 Prompt 规划降低返工率。
5. 在没有 A/B 测试证明 K3 显著优于豆包之前，不建议全量切换。
6. 当前系统的主要容量瓶颈不是 Chat 模型，而是单个图片 Provider、每单五次图片调用、单进程内存任务队列和缺少全局图片并发闸。
7. 严格按当前代码、且不增加全局并发控制时，只能保守承诺 **1 个正在生成默认五张套图的客户**；不能基于现有证据承诺更多同时出图客户。
8. 若只增加一个必要的全局图片并发闸，将总图片并发限制为 3，并经压测确认单张平均耗时在 2～3 分钟，可把第一阶段目标定为：
   - **同时出图客户：1～2 个**
   - **重度出图日活客户：约 50～70 个**，按每客户每天 2 套、每天 8 小时集中使用测算
   - **轻度出图日活客户：约 100～140 个**，按每客户每天 1 套、每天 8 小时集中使用测算

上述客户容量是 `[INFERENCE]`，不是已经完成压测的生产 SLA。

## 4. Kimi K3 的定位

### 4.1 K3 是 Planner / VLM，不是 Renderer

`[OFFICIAL]` Kimi K3 正式模型 ID 为 `kimi-k3`。官方能力包括：

- 文本和视觉输入
- 100 万 Token 上下文
- `reasoning_effort`
- 流式 `reasoning_content`
- JSON Schema 结构化输出
- Tool Calling
- 多轮对话

官方文档展示的是理解图片并返回文本、结构化结果或工具调用，没有提供图片渲染输出 API：

- [Kimi K3 官方说明](https://platform.kimi.com/docs/guide/kimi-k3-quickstart)
- [Kimi 官方模型列表](https://platform.kimi.com/docs/models)

正确定位：

```text
Kimi K3
= 理解用户 + 理解图片 + 规划任务 + 选择工具 + 生成结构化参数

gpt-image-2
= 生成图片 + 编辑图片 + 输出最终视觉资产
```

### 4.2 K3 对现阶段可能带来的好处

| K3 能力 | 对当前产品的直接价值 | 当前是否已具备接入条件 |
|---|---|---|
| 视觉理解 | 直接理解产品图、参考图、已有结果图，减少用户手工描述 | 否，当前消息只支持字符串 |
| JSON Schema | 把用户描述稳定转换为比例、平台、语言、图型、编辑模式等工具参数 | 部分具备，当前有 Tool Schema，但没有严格 `response_format` |
| Tool Calling | 在生成、复刻、编辑、查历史、查价格之间选择正确工具 | 部分具备，当前已有 6 个工具 |
| 长上下文 | 保留品牌约束、历史配方、长会话需求 | 当前价值有限，现阶段对话较短 |
| 复杂推理 | 处理“保留商品、换背景、加卖点文字、按平台规范输出”等复合要求 | 需要 A/B 测试，不能仅凭官方能力宣称优于豆包 |
| 完整视觉质检 | 查看生成结果后给出问题说明和修改建议 | 当前链路尚未把生成结果图片送回 Chat 模型 |

### 4.3 最值得优先验证的三个收益

#### 收益一：减少用户填写和反复澄清

`[INFERENCE]` 如果 K3 能直接读取产品图，它可以辅助识别：

- 商品大类
- 主体数量
- 包装形态
- 主要颜色与材质
- 图中文字
- 适合的画幅和场景

这可以让 Chat 更像“需求翻译器”，但不代表删除必要的用户确认。

#### 收益二：提高工具参数正确率

当前 Chat 的核心不是自由聊天，而是让模型正确选择并填写：

- `generate`
- `clone`
- `edit`
- `query_my_jobs`
- `get_job_recipe`
- `get_pricing_quota`

工具定义位置：

- `image-code/src/design_hub/application/chat/orchestrator.py:59-111`

`[INFERENCE]` K3 的严格 JSON Schema 和工具调用能力有机会降低：

- 缺字段
- 枚举填错
- 不该出图时提前调用
- 复刻和编辑模式选错
- 用户意图与最终 Prompt 不一致

是否真的优于当前豆包必须通过同一组真实业务用例做 A/B 测试。

#### 收益三：降低返工和重生成

K3 本身不渲染图片，但可以通过以下方式间接降低图片成本：

```text
更准确理解产品和目标平台
→ 生成更完整的结构化需求
→ 选择更合适的工作流与 Prompt
→ gpt-image-2 首轮结果更接近预期
→ 减少重生成
```

这是接 K3 最有商业价值的假设，也是最需要验证的假设。

### 4.4 K3 不能直接带来的收益

K3 不会直接：

- 降低 `gpt-image-2` 单张 API 价格
- 提高 APINebula 图片接口并发
- 缩短 `gpt-image-2` 渲染时间
- 解决当前单进程内存队列问题
- 自动统一前端、后端和数据库的三套价格
- 在没有传入图片的情况下获得视觉理解收益

## 5. K3 当前接入差距

### 5.1 消息不支持视觉对象数组

`[CODE]` 当前 `ChatMessage.content` 固定为字符串：

- `image-code/src/design_hub/ports/text_llm.py:22-29`

`[CODE]` 当前用户附件只以 `upload_ids` 文本备注回填给模型，不会把图片本身作为多模态输入：

- `image-code/src/design_hub/application/chat/orchestrator.py:119-137`

K3 官方要求视觉消息的 `content` 是对象数组。因此，仅修改 `base_url` 和 `model` 无法获得 K3 的视觉理解能力。

### 5.2 没有保留完整 assistant message

`[OFFICIAL]` K3 多轮对话和工具调用要求原样回传完整 assistant message。

`[CODE]` 当前工具调用后只重新构造 `content + tool_calls`：

- `image-code/src/design_hub/application/chat/orchestrator.py:184-215`

这不是 K3 官方要求的完整消息回传。

### 5.3 当前丢弃 reasoning_content

`[CODE]` 当前适配器刻意忽略 `reasoning_content`：

- `image-code/src/design_hub/infrastructure/providers/openai_compat_text.py:91-95`

K3 始终开启思考，并使用 `reasoning_effort`。如果要支持 K3 工具调用，必须正确保存和回传所需的 assistant 消息字段。

### 5.4 当前没有 Chat 成本计量

需要至少记录：

- Provider
- 模型 ID
- prompt tokens
- cached tokens
- completion tokens
- reasoning tokens 或供应商可用的细分字段
- 单次 Chat 成本
- Chat 对应的出图 job_id

这属于成本核算的必要能力，不是为了架构完整而增加的过度设计。

## 6. 不接 K3 与接入 K3 的成本对比

### 6.1 测算假设

以下均为 `[INFERENCE]`：

- 每个出图订单包含一次需求规划和一次出图后收尾
- 合计 5,000 输入 Token
- 合计 1,000 输出 Token
- 默认套图 5 张
- 图片上游成本暂按用户提供的 ¥0.50/张
- K3 输入缓存情况以“充分命中”和“完全未命中”形成区间

当前固定 System Prompt 与 6 个工具 Schema 在用户消息前约有 6,278 字符：

- System Prompt：2,486 字符
- Tool Schema：3,792 字符

这是字符数，不是官方 Token 账单，仅用于说明 5,000 输入 Token 的测算并非零上下文假设。

### 6.2 Chat 单价

`[OFFICIAL]` Kimi K3 每百万 Token：

| 项目 | 价格 |
|---|---:|
| 缓存命中输入 | ¥2 |

| 输出 | ¥100 |

官方来源：[Kimi K3 定价](https://platform.kimi.com/docs/pricing/chat-k3)

K3 始终开启思考，`reasoning_content` 会消耗 Token；最终成本取决于实际输出长度。

### 6.3 每个订单成本

| 方案 | Chat 成本/单 | 单张图订单总成本 | 默认五张套图总成本 |
|---|---:|---:|---:|
| 豆包 2.0 Mini | ¥0.0030 | ¥0.5030 | ¥2.5030 |
| 豆包 2.0 Lite | ¥0.0066 | ¥0.5066 | ¥2.5066 |
| 豆包 2.0 Pro | ¥0.0320 | ¥0.5320 | ¥2.5320 |
| Kimi K3，输入充分命中缓存 | 约 ¥0.11 | 约 ¥0.61 | 约 ¥2.61 |
| Kimi K3，输入未命中缓存 | 约 ¥0.20 | 约 ¥0.70 | 约 ¥2.70 |

如果 K3 一单实际产生 3,000 输出 Token，Chat 成本将上升到约 ¥0.31～¥0.40。

结论：

- 默认五张套图中，K3 Chat 约增加 4.4%～8.0% 的供应商成本。
- 单张图订单中，K3 Chat 约增加 22%～40% 的供应商成本。
- 把多张图片组织为一次清晰的订单，比每生成一张都重新进行一次完整 Chat 规划更经济。

### 6.4 每个出图客户的成本

#### 轻度客户：每天 1 套、每套 5 张

| 方案 | 单客户日成本 | 100 个日活客户/月成本，按 30 天 |

| Kimi K3 | ¥2.61～¥2.70 | ¥7,830～¥8,100 |

#### 重度客户：每天 2 套、每天 10 张

| Kimi K3 | ¥5.22～¥5.40 | ¥15,660～¥16,200 |

图片费用仍占总供应商成本的绝大部分。

### 6.5 返工成本的盈亏平衡

按上述假设，K3 相比豆包每单增加约 ¥0.08～¥0.20。

如果每次重生成一张图片成本是 ¥0.50，则 K3 需要平均每单减少：

```text
¥0.08 ÷ ¥0.50 = 0.16 张
¥0.20 ÷ ¥0.50 = 0.40 张
```

即大约做到每 3～6 单少重生成一张，才能仅从供应商成本角度覆盖 K3 的新增费用。

因此，K3 是否值得接入应以“返工率、任务成功率和用户完成时间”判断，而不能只比较 Chat Token 单价。

## 7. 当前系统可以承载多少客户

4. 每天实际出图的活跃客户

### 7.5 增加一个全局并发闸后的容量测算

这不是引入新工作流引擎，只是把当前“每任务最多 3”改为“整个服务最多 3 个上游图片请求”，防止多个客户共同打爆一个 Key。

- 全局图片并发 `C = 3`

```text
每小时图片数 = C × 60 ÷ L
每小时五张套图数 = C × 60 ÷ L ÷ N
                 = 36 ÷ L
```

## 8. 三种方案比较

### 方案 A：继续豆包 Chat + gpt-image-2

优点：

- Chat 成本最低
- 当前代码适配度最高
- thinking 已关闭，延迟和输出 Token 更可控
- 无新增供应商和接入工作

不足：

- 当前具体豆包 2.0 档位和真实账单不可见
- 是否能够稳定理解复杂产品图片和复合要求尚未量化
- 当前 Chat 仍没有 Token 成本记录

适合：

- 先验证产品需求和图片工作流
- 客户主要通过表单给出明确参数
- Chat 只承担轻量澄清和工具选择

### 方案 B：Kimi K3 替换豆包 Chat + gpt-image-2

优点：

- 可使用视觉理解，让 Chat 直接理解产品图和参考图
- 可用严格 JSON Schema 生成工具参数
- 复杂任务规划、长上下文和多轮工具调用能力更完整
- 有机会减少澄清轮次和图片返工

不足：

- Chat 成本上升
- K3 始终思考，延迟和输出 Token 更不稳定
- 当前代码必须补多模态消息、完整 assistant message、reasoning 和 usage
- K3 是否比当前豆包更适合电商图片场景仍为 `[UNKNOWN]`

适合：

- 真实用户需求经常模糊、复杂
- 用户希望“上传图片后直接告诉我怎么做”
- 当前返工和重生成成本已被数据证明较高

### 方案 C：豆包和 K3 双模型动态路由

现阶段不推荐。

原因：

- 增加模型路由、灰度、监控和故障处理
- 当前连单一 Chat 模型的 Token 成本都未记录
- 没有 A/B 数据证明哪些请求值得升级到 K3
- 图片 Provider 才是容量瓶颈

只有在方案 B 的小流量试验取得数据后，才考虑是否让简单请求走豆包、复杂视觉请求走 K3。

4. 记录豆包和未来 K3 的 Token usage 与成本。

### P1：只做 K3 最小可验证接入

4. 支持 `reasoning_effort`。

### P2：做 50～100 条真实业务 A/B

## 10. 建议验收门槛

只有同时满足以下条件，才建议 K3 替换豆包：

1. K3 的工具选择正确率高于豆包。
2. K3 的图片首轮采纳率有可重复提升。
3. 平均每 3～6 单至少减少一次图片重生成，或用户完成时间明显下降。
4. K3 单订单 Chat 成本稳定可观测。
5. P95 Chat 延迟不破坏用户体验。
6. K3 视觉输入、完整 assistant message 和工具调用通过自动化测试。
7. 出图模型仍可独立替换，不依赖 K3 私有业务逻辑。
