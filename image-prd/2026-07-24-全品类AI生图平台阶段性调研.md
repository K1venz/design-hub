## 4. 当前项目代码事实

### 4.1 品类仍是前后端双重写死

后端请求类型固定了五个品类：

```text
FOOD / FASHION / BEAUTY / SHOES / DIGITAL
```

证据：

- `image-code/src/design_hub/application/listing/requests.py:13-15`

该处代码注释直接说明：新增品类需要修改请求类型，并在 Prompt 组装模块增加卡常量。

前端独立维护了同一份品类列表和中文显示名称：

- `image-web/src/lib/listing.ts:99-110`

因此，当前新增一个普通品类至少会影响：

- 后端请求类型
- 后端 Prompt 注册
- 前端品类列表
- 前端中文显示映射
- 相关接口类型生成结果
- 测试

**阶段性判断：** 当前的“注册表”仍然是代码内注册表，不是数据驱动的动态品类中心。

### 4.2 比例和尺寸由前后端分别维护

后端固定支持：

```text
1:1 / 3:4 / 9:16 / 16:9
```

并将多个比例归并到固定像素尺寸。

证据：

- `image-code/src/design_hub/application/listing/sizing.py:1-16`

前端再次维护同一比例集合：

- `image-web/src/lib/listing.ts:10-18`

**风险：**

- 新模型支持新比例时必须修改前后端代码。
- 不同模型的真实尺寸、比例和限制无法独立描述。
- 用户看到的是平台固定比例，而不是当前模型与工作流能力的交集。

### 4.3 套图结构固定为三种图型

前端固定了：

- 白底
- 场景
- 卖点

同时写死：

- 默认配比：`1 / 2 / 2`
- 总张数：`3～10`
- 卖点文案最多 2 条
- 每条最多 12 个字

证据：

- `image-web/src/lib/listing.ts:20-34`
- `image-web/src/components/listing/ListingConfigPanel.tsx:95-145`

后端 Prompt 组装模块也按固定图型生成不同 Prompt：

- `image-code/src/design_hub/application/listing/prompt_composer.py:143-207`

**阶段性判断：** 当前套图不是通用工作流，而是一个固定业务流程。未来增加细节图、尺寸图、对比图、模特图、安装图、材质图或社媒图时，需要继续修改代码。

### 4.4 Prompt 是运行代码常量

当前运行代码包含：

- 平台对应 Prompt 片段
- 地区和语言片段
- 五个品类的长 Prompt
- 白底、场景、卖点图型 Prompt
- 复刻模式 Prompt
- 编辑模式 Prompt

证据：

- `image-code/src/design_hub/application/listing/prompt_composer.py:3-140`
- `image-code/src/design_hub/application/listing/prompt_composer.py:143-367`

这些 Prompt 虽然被封装成 Registry，但其来源仍是 Python 常量。

**影响：**

- 运营不能独立修改。
- 无法自然实现版本、灰度、发布和回滚。
- 无法按租户、场景、模型或实验组选择不同版本。
- Prompt 改动与代码发布绑定。

### 4.5 模型注册仍依赖固定枚举

当前领域模型固定声明：

- `gpt-image-2`
- `seedream-5`
- `wanxiang-2.7-pro`
- `lingdong-2`

证据：

- `image-code/src/design_hub/domain/enums.py:4-8`

- `image-code/src/design_hub/application/registry.py:5-20`

这意味着未知模型无法仅通过数据库配置成为正式运行模型。

### 4.6 管理后台模型配置尚未形成动态路由

管理后台已经支持保存：

- 单价

- Base URL
- 上游模型 ID

但运行时仍有明显限制。

#### 限制一：任意模型名不会进入运行时成本映射

`unit_cost_map()` 只接受命中固定 `ModelName` 枚举的数据库记录：

- `image-code/src/design_hub/application/admin/model_config_service.py:66-77`

#### 限制二：enabled 尚未进入实际模型路由

同一段代码明确显示，`enabled` 当前没有被正式路由消费。

#### 限制三：默认配置只驱动一个固定出图槽

当前默认模型连接最终仍注册到 `ModelName.GPT_IMAGE_2`：

- `image-code/src/design_hub/composition.py:66-150`
- `image-code/src/design_hub/composition.py:226-243`

#### 限制四：切换默认模型需要重启

默认连接在应用装配阶段读取，未形成运行时热更新路由。

**阶段性判断：** 当前管理后台具备“连接配置”的部分能力，但还不是完整的模型注册中心、能力中心或动态路由中心。

当前图片 Provider 只有一个核心方法：

## 5. Kimi K3 接入判断

### 5.1 官方已经确认的能力

截至 2026-07-24，Kimi 官方开放平台已经正式列出 `kimi-k3`。

官方资料确认：

- 原生视觉理解
- 100 万 Token 上下文
- OpenAI SDK 风格的 Chat Completions 接口
- JSON Schema 结构化输出
- Tool Calling
- `low / high / max` 三档 `reasoning_effort`
- 流式返回推理内容和最终内容

官方来源：

- [Kimi K3 官方快速开始](https://platform.kimi.com/docs/guide/kimi-k3-quickstart)
- [Kimi 官方模型列表](https://platform.kimi.com/docs/models)
- [Kimi 模型参数参考](https://platform.kimi.com/docs/api/models-overview)
- [Kimi List Models API](https://platform.kimi.com/docs/api/list-models)

### 5.2 Kimi K3 不应被当作图片渲染模型

当前官方资料描述的是：

- 视觉内容理解
- 文本输出
- 结构化输出
- 工具调用
- 智能体工作

本次没有发现 Kimi K3 官方图片输出端点。

因此，Kimi K3 更适合进入 Planner/VLM 层，承担：

- 用户需求理解
- 输入图片分析
- 场景和品类识别
- 需求转结构化参数
- 工作流选择
- Prompt 规划
- 工具调用
- 结果质检

真正生成图片仍应由独立 Renderer Provider 完成。

### 5.3 当前文本 LLM 适配器不能直接宣称完整兼容 Kimi K3

当前项目的文本 LLM 适配器已经支持：

- OpenAI 风格 Chat Completions
- 流式文本
- Tool Calling
- Base URL、Key 和模型配置

证据：

- `image-code/src/design_hub/infrastructure/providers/openai_compat_text.py:26-119`

但还存在两个关键差距。

#### 差距一：消息内容只能是字符串

当前 `ChatMessage.content` 是 `str`：

- `image-code/src/design_hub/ports/text_llm.py:22-29`

Kimi K3 的视觉输入要求消息内容能够表示图片和文本对象数组。

#### 差距二：当前适配器丢弃 reasoning_content

当前代码刻意不读取和保存 `reasoning_content`：

- `image-code/src/design_hub/infrastructure/providers/openai_compat_text.py:91-95`

Kimi 官方要求 K3 多轮对话和工具调用时原样回传完整 assistant message。

**结论：**

- 简单单轮文本调用可能可以通过配置接入。
- 完整的多模态、工具调用和多轮 K3 Agent 不能只通过替换 `base_url` 和 `model` 完成。
- 需要重构消息模型和 LLM Capability Contract。

## 6. 外部平台公开机制

### 6.1 ComfyUI：工作流图与节点定义

公开事实：

- 工作流是 JSON 节点图。
- 节点之间通过连接表达数据依赖。
- API 可以提交完整工作流。
- `object_info` 可以返回可用节点定义。
- 工作流可以作为模板保存和复用。

官方来源：

- [ComfyUI Cloud API Overview](https://docs.comfy.org/development/cloud/overview)
- [ComfyUI Workflow JSON](https://docs.comfy.org/specs/workflow_json_0.4)
- [ComfyUI Object Info](https://docs.comfy.org/api-reference/cloud/node/get-all-node-information)
- [ComfyUI Workflow Templates](https://docs.comfy.org/custom-nodes/workflow_templates)

项目启示：

- 生成流程应保存为版本化工作流，而不是写在 Service 调用顺序里。
- 节点应自描述输入、输出和类型。
- 业务场景可以绑定工作流模板。

### 6.2 Replicate：每个模型拥有独立 Schema

公开事实：

- 每个模型版本可以公开自己的 OpenAPI 输入输出 Schema。
- 模型调用统一进入 Prediction 生命周期。
- 支持异步状态、取消、Webhook 和输出保存。

官方来源：

- [Replicate OpenAPI Schema](https://replicate.com/docs/reference/openapi/)
- [Replicate HTTP API](https://replicate.com/docs/reference/http/)
- [Replicate Predictions](https://replicate.com/docs/topics/predictions/create-a-prediction/)

项目启示：

- 不应要求所有模型共享同一组参数。
- 可以统一任务生命周期，但保留模型自身 Schema。
- 动态表单可以基于模型 Schema 和产品策略生成。

### 6.3 fal.ai：统一队列生命周期 + 模型独立 Schema

公开事实：

- 不同模型使用相似的调用和队列生命周期。
- 支持提交、状态、结果、取消和 Webhook。
- 每个模型页面提供输入输出 Schema。
- 模型覆盖图片、视频、音频、视觉和 3D。

官方来源：

- [fal Model APIs](https://fal.ai/docs/documentation/model-apis/overview)
- [fal Asynchronous Inference](https://fal.ai/docs/documentation/model-apis/inference/queue)
- [fal Model API Reference](https://fal.ai/docs/model-api-reference)

项目启示：

- Job 状态可以统一。
- 参数不应强行统一。
- 模型能力与队列能力应分开描述。

### 6.4 Stability AI：按照能力而不是品类组织 API

公开事实：

Stable Image Services 将能力分为：

- Generate
- Edit
- Control
- Upscale

具体能力继续拆分为生成、局部编辑、扩图、结构控制、风格控制和不同放大方式。

官方来源：

- [Stability Stable Image Overview](https://platform.stability.ai/docs/getting-started/stable-image)
- [Stability API Reference](https://platform.stability.ai/docs/api-reference)

项目启示：

- 底层平台应该首先定义视觉能力。
- “食品、美妆、服装”属于产品场景层，不应直接成为模型接口层。

### 6.5 Recraft：多产物类型与模型兼容范围

公开事实：

Recraft 支持：

- Raster
- Vector
- Mockup
- Background
- Inpainting/Outpainting
- Remove Background
- Vectorize
- Upscale
- Styles

API 文档会明确标注某参数或操作兼容哪些模型。

官方来源：

- [Recraft API](https://www.recraft.ai/api)
- [Recraft Endpoints](https://www.recraft.ai/docs/api-reference/endpoints)
- [Recraft Getting Started](https://www.recraft.ai/docs/api-reference/getting-started)

项目启示：

- 输出类型也应是能力的一部分。
- 字段可见性需要受模型兼容性约束。
- 用户场景可以组合多种视觉操作。

### 6.6 InvokeAI：统一管理本地模型和外部模型

公开事实：

- 提供模型管理器。
- 支持节点工作流。
- 工作流可以用于生产场景。
- 本地模型和部分外部 API 模型都可以进入画布和 Workflow Editor。
- 外部模型会根据供应商限制暴露不同能力。

官方来源：

- [InvokeAI 官方仓库](https://github.com/invoke-ai/InvokeAI)
- [InvokeAI Releases](https://github.com/invoke-ai/InvokeAI/releases)

项目启示：

- “模型已注册”不等于“模型支持所有能力”。
- Capability 必须单独描述。
- 本地和云端模型可以共享上层任务协议，但不能假设参数完全一致。

### 6.7 Canva：用户操作任务，不操作模型

公开事实：

Canva 将生成、编辑、扩图、尺寸转换、翻译和设计模板放在统一编辑体验中。普通用户选择的是设计任务和内容，不需要理解底层模型参数。

官方来源：

- [Canva Editing and Designing](https://www.canva.com/help/editing-designing/)
- [Canva Magic Studio](https://www.canva.com/en_in/newsroom/news/magic-studio/)

项目启示：

- 普通用户入口应面向目标任务。
- 模型、Provider、采样参数应由系统策略管理。
- 高级工作流和普通场景表单需要分层。

### 6.8 Adobe Firefly：操作型 API

公开事实：

Adobe Firefly 对生成、填充等操作提供不同 API 契约，填充任务明确区分源图、蒙版和 Prompt。

官方来源：

- [Adobe Firefly Fill Image API](https://developer.adobe.com/firefly-services/docs/firefly-api/guides/how-tos/firefly-fill-image-api-tutorial)
- [Adobe Firefly Placement](https://developer.adobe.com/firefly-services/docs/firefly-api/guides/concepts/placement/)

项目启示：

- 不同视觉操作需要明确的输入输出契约。
- 不应把所有操作压缩为一个无限扩张的 `generate()`。

## 7. 行业共性总结

基于以上公开资料，可以确认成熟平台普遍采用以下组合，而不是“一个品类一个固定流程”：

1. **用户场景层**：面向海报、电商、Logo、Mockup、社媒等用户任务。
2. **表单 Schema 层**：描述用户可填写字段、默认值和校验。
3. **工作流层**：组合理解、生成、编辑、放大、排版和质检步骤。
4. **能力层**：描述模型是否支持某种操作。
5. **模型与 Provider 层**：负责具体协议和供应商差异。
6. **统一任务层**：负责队列、状态、取消、重试、成本和审计。
7. **资产层**：保存输入、中间产物、输出及生成血缘。

需要特别区分：

- 统一任务生命周期，不等于统一所有模型参数。
- 统一用户体验，不等于所有场景使用同一个工作流。
- 全品类，不等于预先写完所有品类枚举。

## 8. 推荐的目标架构方向

```text
Scene Recipe
    ↓
Form Schema
    ↓
Workflow Version
    ↓
Capability Router
    ↓
Provider Driver
    ↓
Generation Job + Asset + Cost + Audit
```

### 8.1 Scene Recipe

负责用户场景：

- 场景名称
- 用户目标
- 默认工作流
- 默认字段
- 推荐参数
- 可用范围
- 展示和运营配置

新增普通场景原则上不需要增加前后端枚举。

### 8.2 Form Schema

负责动态表单：

- 字段类型
- 默认值
- 枚举选项
- 校验规则
- 显隐条件
- 字段联动
- 排序与分组
- 运营覆盖
- 版本

用户最终字段应由以下交集产生：

```text
场景字段
∩ 工作流输入
∩ 模型能力
∩ 租户和运营策略
```

### 8.3 Workflow Definition / Version

负责：

- 节点
- 输入输出
- 数据依赖
- 条件分支
- 并行执行
- 失败策略
- 工作流版本
- 灰度发布
- 回滚

建议节点能力包括：

- 理解
- Prompt 规划
- 生成
- 编辑
- 扩图
- 抠图
- 换背景
- 放大
- 排版
- 质检
- 存储

### 8.4 Capability Registry

模型不能只记录名称和价格，还应描述：

- 支持的操作
- 输入模态
- 最大参考图数量
- 比例和尺寸
- 输出类型
- 是否支持文字
- 是否支持蒙版
- 是否支持风格参考
- 是否支持异步任务
- 速率限制
- 价格

### 8.5 Provider Driver

Provider Driver 负责：

- 鉴权
- 请求转换
- 响应转换
- 错误映射
- 任务查询
- 取消
- Webhook
- 供应商特定参数

Provider Driver 是正式架构模块，不是兼容旧逻辑的临时补丁。

### 8.6 Planner 与 Renderer 分离

建议拆为两个注册中心。

#### Planner Provider

候选包括 Kimi K3 和其他 LLM/VLM，负责：

- 需求理解
- 视觉理解
- 结构化输出
- 工作流规划
- 工具调用
- 结果质检

#### Renderer Provider

候选包括 GPT Image、Seedream、Flux、Recraft、Ideogram、Stability 等，负责：

- 生成
- 编辑
- 扩图
- 换背景
- 结构控制
- 放大
- 矢量化

这样可以独立替换规划模型和图片模型。

## 11. 阶段性结论

1. 当前项目已经存在 Provider、Registry、任务队列和模型配置等架构雏形，但还没有形成真正的数据驱动全品类平台。
2. 品类、比例、图型、套图结构、Prompt、模型枚举和工具流程仍然存在明显写死。
3. 当前模型后台配置没有完整进入运行时动态路由。
4. 当前统一 `generate()` 接口无法自然覆盖未来所有视觉操作。
5. Kimi K3 可以作为 Planner/VLM 接入，但不应被视为图片渲染模型。
6. 当前文本 LLM 适配器需要支持多模态消息和完整 assistant message，才能完整适配 Kimi K3。
7. 推荐采用“场景 Recipe + 动态表单 + 版本化工作流 + 能力路由 + Provider Driver”的目标结构。
8. 下一步应先完成全量代码审计和目标领域模型设计，不应直接开始大规模改代码。
